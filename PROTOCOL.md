# Tako Runtime Protocol

This document records the small set of contracts shared by the CLI, server, and SDKs. Exact message fields and serialized shapes live in typed code and tests.

The protocol version is `0`. Breaking changes are allowed until protocol v1. Change every producer and consumer in the same update. Do not add compatibility shims.

Native enrollment and local device keys use version 2. Requests bind distinct SSH,
WireGuard, and X25519 secret-encryption keys. Membership and network state
records replicate between servers through Corrosion; clients pull and publish
records through signed, pinned HTTPS. Secret records are sealed to each reader;
records of kinds that are not secret, such as the active backup key ID, are
plaintext. A server that cannot open a record yet returns it without the
reader's key, and the client asks another server for it. Invitations are single-use capabilities consumed by
their issuing server. Old native identities require fresh enrollment. Only full
members read or publish secret records; deploy clients receive none.

A member's `permissions` is `"full"` or `{"deploy": ["app/env", ...]}`. Full
members (every server, and clients added without `--deploy`) may do everything,
including SSH to the `tako` account and WireGuard peering. Deploy clients may
only release to their scopes: `prepare_release`, `prepare_release_upload`,
`prepare_deploy`, `deploy`, `run_release`, `finalize_release`,
`cleanup_prepared_deploy`, `cleanup_release`, `snapshot_database` and
`migrate_database` for their app, `secrets_digest`, `status`, `list_releases` and
`rollback`. Every other management command and log reads need full access. A
deploy client may make an environment's first deploy and change its routes, SSL
provider and plain storage and backup bindings; changing database bindings needs
full access. Servers reject a deploy or rollback route that another app environment
already claims, for every client. From a deploy client they also reject a new
route that overlaps another app environment's route (it could take some of its
requests); routes the environment already holds may stay. Servers neither peer with deploy clients nor authorize
a shell for them. Every laptop member carries its client name; a laptop
without one is invalid. Rows from earlier versions are not read.
Revocation applies only to the revoked device: an approval stays valid when its
approver was live, unrevoked and validly approved at the approval's
`created_at`. A device cannot revoke itself, and the last full client cannot be
revoked.

Tako has one active protocol version. The CLI, server, and every deploy artifact must declare that exact version; compatibility does not negotiate version ranges or capability sets. Deploy artifacts record it as `protocol_version` in `app.json`.

Deploy artifacts may also record the Tako SDK the app is built against as `sdk` in `app.json`: `{ "language", "name", "version" }`, where `language` is `javascript`, `go`, or `rust`. The CLI reads it from the app's dependency files at deploy time: the installed or locked `tako.sh` package, the `tako.sh` requirement in `go.mod` (`(devel)` when a `replace` points at a local directory, or the replacement module and version), or the `tako` crate in `Cargo.lock`. It is omitted when no SDK is found, including prebuilt images, Compose projects, and containers with `container_options.sdk = false`. The server reports it in `list_releases` and never gates on it.

Normal deploys check the CLI/server protocol before parallel deployment starts. After upload, the server checks the artifact again before preparing dependencies, running a release command, synchronizing workflows, or starting app processes. `--force` bypasses only these version gates so an operator can attempt an incompatible deploy; normal validation and readiness checks still apply.

Release upload plans report `upload_required` and `preparation_required` independently. Reusing a retained archive can skip upload while still requiring `PrepareRelease` to restore production dependencies and container preparation before deployment.

No management command carries secret values. Before a deploy, the CLI publishes its secret drafts and sends `secrets_digest { app, published }` to the leader server, which waits until it holds every published record version (`{ kind, name, revision }`) and returns `{ digest }`: a hash over the app environment's current record versions, deletions included. `PrepareRelease`, `RunRelease`, `PrepareDeploy` and `Deploy` carry that `secrets_digest`. Each target server waits, bounded, until its own digest matches, then opens the values with its own key grants through the local network agent and supplies app secrets, provider credentials (`ssl.cloudflare`, `postgres_url`), S3 access keys and backup keys itself. Clients send bindings without secret parts: S3 storage bindings name their `resource`, the SSL binding carries only the provider, and the backup binding has no keys; servers drop any secret parts a client sends. A `Deploy` without a digest keeps the secrets and credentials the server last applied. Preparation uses the pinned app secrets, including Compose interpolation on a first deploy, without persisting them; activation persists them after preparation succeeds. `BackupNow` with a backup binding fills its keys from the environment's current values. Rollback reuses the release's last-applied values. `get_secrets_hash` returns only a hash of the last-applied app secrets.

Server upgrades run the candidate binary in check-only mode before reload. The candidate checks the invoking CLI version and every active release, then repeats the check after the new process is ready. A mismatch aborts the upgrade. If a failure happens after reload starts, Tako restores and restarts the previous binary before leaving upgrade mode. `tako network server upgrade --force` permits an incompatible attempt but does not disable readiness or rollback.

Before the controlled reload, the CLI writes a one-shot upgrade-owner marker under the server data directory. The candidate consumes it and preserves the matching persisted upgrade fence through state restoration and the post-readiness check. An ordinary reload has no marker, so it still clears a stale upgrade lock.

## Transport boundaries

Tako has two control paths with different trust boundaries.

- The management path handles deploys and operator commands. Local server control uses the management Unix socket. Remote management exposes the same operations through signed HTTP requests on the configured private management address.
- The internal path handles workflow RPCs and server-side channel publishing. Each command carries its app identity. The production Unix socket authenticates the connecting peer's Unix identity against that app; the bootstrap token authenticates internal HTTP probes, not these socket commands.

The Unix transports use newline-delimited JSON. `tako-socket` caps one frame at 1 MiB. A connection can carry successive request/response pairs; SDK clients may pool and reuse connections. Streaming responses are defined by the owning API.

Management-only commands are rejected on the internal socket. Runtime-only commands are rejected on the management socket. Both paths share `tako_core::Command` so message shapes cannot drift between duplicate enums.

## Internal socket error replies

Every reply is `tako_core::Response`: `{"status":"ok","data":...}` or `{"status":"error","message":"...","code":"..."}`. `message` is free text for logs and is not a contract. `code` is present only where an SDK or app must branch; a reply without it is unclassified, and management replies never carry one. Readers treat a code they do not know as unclassified. Codes are the entry names of the `socket` scope in `errkit.json` (generated into `tako-core/src/error_codes.rs`, named by `tako_core::ErrorCode::name`):

| `code`                   | Meaning                                                                                                                                                            | Replies to                                                                                            |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------- |
| `run_not_owned`          | The run is no longer owned by this claim (lease reclaimed, cancelled, finished).                                                                                   | `heartbeat_run`, `save_step`, `complete_run`, `cancel_run`, `fail_run`, `defer_run`, `wait_for_event` |
| `run_id_conflict`        | The supplied run ID belongs to a different workflow or payload.                                                                                                    | `enqueue_run`; network `enqueue`                                                                      |
| `invalid_request`        | The command is malformed, not accepted on this socket, or has an invalid run ID, address, channel payload, or close target. Retrying cannot succeed.               | any command; network requests                                                                         |
| `channel_unknown`        | The publisher's loaded build, or the recipient app, does not define the channel.                                                                                   | `channel_publish`, `channel_close`; network `publish`                                                 |
| `channel_params_invalid` | Params are not a flat object of at most 16 KiB, name a null or reserved param, or fail the params schema.                                                          | `channel_publish`, `channel_close`; network `publish`                                                 |
| `channel_closed`         | The stream has a retained close marker.                                                                                                                            | `channel_publish`; network `publish`                                                                  |
| `signal_inbox_full`      | A run-addressed signal would take the run's inbox past 1,000 entries or 8 MiB of payload. Nothing was stored.                                                      | `signal` with `run_id`                                                                                |
| `unavailable`            | Draining, an unhealthy worker, network or publisher overload, an unreachable destination, the stream limit, or a busy or disconnected workflow store. Retry later. | `enqueue_run`, `network_call`, `channel_publish`, `channel_close`, workflow commands                  |

SDKs decide lost ownership only from `run_not_owned` on a worker write, never from message text: other messages, such as the `run_id_conflict` one, echo caller-chosen values. A network recipient replies with the same shape; a rejection from its own internal socket keeps its code, not its message. JavaScript exposes the code as `TakoError.reason` (with `code: "TAKO_RPC_ERROR"`), Go as `*ServerError.Code` matched by sentinels such as `ErrRunNotOwned` with `errors.Is`, and Rust as `tako::ErrorCode` (`ErrorCode::of(&io::Error)` for network calls, `StoreError::Rejected(Option<ErrorCode>)` for Store invalidations).

## Server-local cache

The server-local cache uses the internal socket, not a network address.
`{command:"cache", app, operation:"get"|"delete", key}` reads or removes a key
in the authenticated app/environment; optional `shared:true` selects a separate
store shared by apps on that server in the caller's environment. Omitted or
false selects the private store. The caller cannot select another environment.
`"put"` also takes `json` (serialized
JSON, at most 256 KiB) and a positive integer `ttl_ms`. Keys are nonblank and
at most 1 KiB of UTF-8. Get replies carry the JSON **string** on a hit (including
`"null"`) or `null` on a miss. Writes reply with `null`. Management rejects
this command. `tako-server` owns private `data/tako/cache.redb` files and
`<server-data>/shared-cache/<environment-digest>/cache.redb`; SDKs never open them.
The dev daemon and one-shot local run host use the same implementation.

## Network primitives

`network_call` is an internal-socket command with `{app, address, request}`. `app` remains the authenticated caller identity. `address` is a bare primitive name or `namespace.primitive`; a qualified namespace selects another app in the caller's environment. URLs, paths, extra dots, and caller-selected environments are rejected. `tako-core/src/network.rs` owns the invocation shapes and address grammar.

Requests are `call` with JSON input for direct handlers, `enqueue` with payload and options, `result` with a run ID, or `publish` with message and params. Direct handlers run without enqueueing and return JSON. The recipient supplies workflow retry defaults or channel lifecycle settings. Enqueue acknowledges a run ID; publish acknowledges the stored or ephemeral message. Result reads return null for a missing workflow/run pair, otherwise `{status,result,error}`. Result reads are short requests; clients poll rather than holding routing capacity while a workflow runs. Network delivery is attempted once. A separate client socket pool reserves storage capacity, and both client and server reject network overload immediately so nested handlers cannot queue behind waiting ancestors.

For native networks, the router selects an authenticated placement and sends `POST /_tako/network` over the private mesh. The body carries an agent-signed invocation under `tako-network-invocation-v1`, binding network, source server, destination server, caller app/environment, target app/environment, issuance time, nonce, and invocation. The caller comes from authenticated socket credentials. Protected local agent IPC signs the proof; proxies do not read identity keys. Receivers require a fresh admitted server identity matching the actual WireGuard peer, verify destination and signature, and reject expiry or replay. Generic enrolled laptops and Compose peers cannot invoke this path. Proofs cannot be relayed to another placement. Public ingress rejects it. Only after verification does the proxy wake the app and send `POST /network` with its internal host/bootstrap token; the response must echo the token. Local development and non-network same-server routing use that recipient endpoint directly. Requests and responses are bounded to 1 MiB; redirects and environment HTTP proxies are disabled. Management endpoints reject `network_call`.

JavaScript implements recipient dispatch, including flat `<app_root>/network-handlers/` functions addressed by filename. JavaScript, Go, and Rust implement socket callers. `tako gen` exports `tako-schema.json` (JSON Schema 2020-12 with version 1 `x-tako` app/primitive metadata). Root `schemas` imports local paths or HTTP(S) URLs. A committed `tako-schema.lock` embeds hashed remote schemas; updates are explicit. Consumers compile standalone TypeScript contracts (`tako.imports.ts`), Go DTOs (`tako_imports.go`), or Rust Serde DTOs (`tako_imports.rs`). Go DTO and Rust schemars exporters describe native JSON contracts without adding recipient dispatch. `tako.exports.d.ts` remains a JavaScript convenience export. Generation changes no package exports. Type imports do not alter network authorization or runtime registration.

## Process bootstrap

Native app and worker processes receive the bootstrap envelope as JSON on file descriptor 3. The envelope contains the app-scoped internal token, decrypted secrets, storage bindings, database connections (`databases`: binding name → `{ "url", "authToken" }`), and KV store connections (`kv`: binding name → `{ "url" }`, a `redis://:<token>@127.0.0.1:9846` URL). `tako-core::bootstrap` is the only server-side serializer for this shape; SDKs ignore keys they do not know, so a server may add one before apps upgrade. Container processes receive no database or KV store connections.

Native HTTP processes receive `HOST=127.0.0.1` and `PORT=0`. The SDK binds an available loopback port, completes any readiness hook, and writes the resolved port to file descriptor 4. The server does not route traffic to the process before this handshake completes.

Tako-managed processes also receive `TAKO_APP_NAME` and `TAKO_INTERNAL_SOCKET`. SDKs require those variables as a pair before making workflow or channel RPCs.

Container processes receive the same bootstrap envelope through `TAKO_BOOTSTRAP_DATA`. HTTP containers bind `HOST=0.0.0.0` and `PORT=3000`; they do not use file descriptors 3 and 4. Container workflow processes receive the internal socket mount and the same app identity contract.

Container release artifacts carry `container_options`, including the container port, persistent data mount, optional numeric user mapping, and SDK mode. The host app data directory is mounted at the configured container path and `TAKO_DATA_DIR` is translated to that path, for HTTP containers and container workflow processes alike. Plain containers (`sdk = false`) receive no bootstrap token and use an ordinary HTTP health probe. Only explicitly selected secrets become environment variables. SDK containers retain the authenticated `/status` contract during both startup and steady-state health checks.

Compose releases carry `release_kind = "compose"` and the shared `ComposeConfig`. They represent one application group on one server. `ComposeServiceConfig` (from `services.<name>.x-tako`) carries `envs`, `http` and `sdk`; `http` and `sdk` are omitted when false. Routes in any environment, including `development`, or `http: true` make a service an HTTP app with a service-scoped backend pool. `sdk: true` without routes or `http` makes it an SDK worker or job. An `x-tako` with none of these fails validation. Untagged services remain ordinary Docker services. Source metadata is captured in `ComposeConfig.services`, validated before Docker normalization, and resolved for the deployment environment. HTTP ports come from Compose expose/ports or image EXPOSE; an SDK HTTP app with no candidate uses 3000. Readiness of plain HTTP apps uses Docker health plus a private `HEAD /` HTTP response check (any status; `Host: localhost`). The server prepares immutable service images without persisting interpolated secrets. Project identity is derived from the persistent app data path, independent of release version. Production creates immutable service generations with stable network aliases and resources; fingerprints compare resolved configuration and image IDs. Unchanged containers are adopted. Each tagged stateless app defaults to start-first replacement with readiness and draining; writable persistent volumes and other services default to stop-first. `deploy.update_config.order` and `monitor` control per-service updates. A pending marker precedes mutations; active release, routes, per-release route/source-IP history, and encrypted credentials commit atomically. Recovery reconciles the committed release and cleans abandoned generations. HTTP instance cleanup owns only its container. Named volumes survive stop and deletion and remain outside Tako app-data backups. Referenced release files are protected from pruning. `AppStatus.kind` is `application_group` for Compose; `applications` contains each `x-tako` service's identity, `kind` (`http` or `worker`), `sdk`, state, routes and instances, including explicitly stopped apps with no instances. A worker's state comes from its containers. `AppStatus.services` reports original service names, state, health, and exit codes; `services_error` reports query failures.

Compose services with `sdk: true` receive the container runtime contract for their group, which is one Tako app: `TAKO_APP_NAME` (the group's deployment ID), `TAKO_INTERNAL_SOCKET=/run/tako/internal.sock`, `TAKO_BOOTSTRAP_DATA` (`{token, secrets, storages, databases: {}, kv: {}}` with every group secret and S3 storages only), `TAKO_DATA_DIR=/tako/data`, `TAKO_BUILD` and `ENV`, plus `HOST=0.0.0.0` and the selected `PORT` for HTTP apps. The group's socket directory `{data_dir}/runtime/compose/<project>` (root `runtime/compose` 0700, project 0711) is mounted read-only at `/run/tako`; the app data directory is mounted read-write at `/tako/data` with its group added. The socket there is a pinned listener for the group: it serves the shared socket's command set, accepts a command only when its `app` is the group (`internal socket app mismatch` otherwise), checks no Unix identity, and has mode 0666. `internal.sock` is a relative symlink to `internal-<pid>.sock`, so it resolves through the mount and a successor process re-binds it in place; the shared socket's link is relative too. The group token is a random 32-byte value stored encrypted with the group's credentials and committed with the deployment that first has an SDK service; it is reused afterwards and is the internal token of the group's SDK HTTP instances. Every `x-tako` service also receives the non-secret `TAKO_COMPOSE_SERVICE=<service>`, and SDKs use it to explain a missing `sdk: true` on first use of secrets, channels or workflows. SDK service definitions reach Docker on stdin after fingerprinting; their fingerprints add the envelope digest, `TAKO_BUILD` and the mounts, so they are replaced on every deploy and secret change while plain services are not. Production never puts the envelope in the Compose client's environment. SDK HTTP readiness is `GET /status` with `Host: <app>.tako` and `x-tako-internal-token`; it requires a 2xx response that echoes the token, in addition to Docker health. A deploy fails if an SDK service sets the runtime variables (or `HOST`/`PORT` for HTTP apps) itself or mounts over `/run/tako` or `/tako/data`, or if the group binds local storage. Channel, presence and store requests are authorized by the SDK service that owns the matched route, with the group token; on a route owned by a plain service the proxy answers 404 with an error that names `sdk: true`. Publishes from any SDK service go to the group's channel store.

A Compose group with an SDK service has a workflow runtime whose workers are external: always-on Compose services that use the group's socket. Its supervisor never spawns processes, waking and schedule bootstrap do nothing, and enqueue is accepted unless the runtime drains. A deploy prepares and installs the new release's runtime before starting its SDK containers; a failed rollout reinstalls the previous release's runtime. Only a worker of the current build registers schedules; schedules stored before a server restart stay active. Compose groups with SDK services reject Tako-managed worker commands, counts and concurrency.

Management `start` and `stop` carry `{app, service?}`. Omitting `service` selects the deployment; for Compose this includes all Docker services. A service selector must name an `x-tako` service. Scale without a service selects the group's only HTTP app. Group and per-app stopped intent is stored separately from replica counts and committed with deployment state, so deploy, rollback, and restart preserve both. Starting a group preserves individually stopped apps; starting an app while its group is stopped is rejected. Explicitly stopped dependencies remain stopped when their consumers start or redeploy, even with `depends_on`. Scale updates the configured count without resuming stopped apps. Child deletion is rejected; remove a service through a group deployment or delete the entire group. Native stop also prevents request-triggered cold starts and stops workflows; native start resumes workflows and the configured minimum, warming one instance when the minimum is zero.

## Local object storage

The Rust development and production proxies own signed `/_tako/storages/<binding>/<key>` GET/PUT routes. The SDK only signs URLs; it does not handle these requests or read/write local storage files. Proxies select the application from its matched route, then validate that app's binding and HMAC before opening storage. The signed payload is `METHOD\nBINDING\nENCODED_KEY\nEXPIRES` using the binding's signing key and HMAC-SHA256.

`tako-storage` delegates object operations to Apache `object_store`. Local roots are in the application's private Tako data area; app-owned data is only a capability-confined migration source. Development roots also include a stable hash of the registration/config identity. Object and directory writes are synced before acknowledgment. Local uploads share the production 128 MiB request-body limit. Storage requests do not require a running app worker.

Local binding paths and logical object keys use `object_store::path` encoding in the private filesystem, including during legacy imports. This keeps literal `%`, `#`, and backslash characters distinct from backend staging names. Signed URLs continue to encode the original logical key.

## Health probes

The server probes `GET /status` with `Host: <app>.tako` and an `X-Tako-Internal-Token` header. Tako SDK adapters own this internal endpoint. A healthy response must be successful and echo the token header so an unrelated public `/status` route cannot satisfy the probe.

The token is infrastructure-only. SDKs must not expose it to application code or public responses.

`AppStatus.recovery` is present only while the server has replaced instances since the last deploy, scale, or stable minute. It carries `restart_count`, `last_exit` (`reason` of `crashed`, `unhealthy`, or `failed_to_start`; the observed `exit_code` or `signal` when the process exited by itself; `at_unix_secs`), and `next_restart_at_unix_secs` while replacement is backing off.

## Workflow claim ownership

`ClaimRun.worker_id` identifies a worker process for concurrency accounting.
Every successful claim returns a fresh opaque `RunPayload.worker_id`. The worker
must echo that returned identifier on all heartbeats, checkpoints, and lifecycle
mutations. Reclaiming a run produces a different owner even within the same
process, so a delayed earlier attempt cannot mutate the new attempt's state.
SDK process identities also include randomness to avoid PID reuse across hosts
or restarts. Ownership checks fence database writes, not external side effects;
workflow execution remains at least once.

## Workflow results and child calls

`CompleteRun` carries a JSON `result` (null for no return value). The store atomically commits it with the succeeded status, guarded by the current claim owner. SQLite and Postgres persist it in `runs.result` and remove it with retained run history. `GetRunResult {app,name,id}` is an authenticated runtime-socket command; a mismatched workflow name is a missing run, and the app/environment scope is enforced by the same peer authentication as enqueue. It is not a management command.

JavaScript `.run()` combines enqueue and result waiting. In a workflow, the SDK saves a child ID and call identity before enqueueing, repeats an uncertain enqueue with that ID, and checkpoints the terminal outcome. A pending child of the same app parks the parent with `WaitForRun {app,id,worker_id,step_name,target_name,target_id,timeout_at_ms?}`, which replies `{delivered}`. The parked run waits on the reserved event `__run:<target_id>`, and every transaction that finishes the target wakes it with the target's `RunResult` saved as the step result: completion, bail, final failure, operator cancel, and a reclaim that ends the run dead. A target that has already finished, is missing, or belongs to another workflow than `target_name` saves its outcome at once, and the run is due immediately; a timeout saves `null`. Postgres locks the target's row before the waiting run's, the same order as the finishing transaction, so a parent can never park after its child finished unseen. Children reached through a network handle may live in another store, so the SDK polls them with `DeferRun` instead, backing off from one second to one minute. Either way the parent releases its claim/concurrency slot without spending a retry. Result waits checkpoint their deadline across replay; a timeout does not cancel the child. Named `ctx.run` steps scope child-call order. IDs remain deduplicated only while child history is retained. Detached `.enqueue()` and direct handler `call()` do not gain automatic workflow checkpoints.

## Workflow signals

`WaitForEvent {app,id,worker_id,step_name,event_name,timeout_at_ms?}` parks the claimed run on an event and replies `{delivered}`. `Signal {app,event_name,payload,run_id?}` delivers a payload; event names starting with `__` are reserved for Tako and rejected with `invalid_request`.

Without `run_id`, a signal is a broadcast: every run parked on `event_name` gets the payload as its step result and is due now. Nothing is kept for a run that is not parked yet. The reply is `{woken}`.

With `run_id`, a signal goes to that run only and the reply is `{status}`:

| `status`    | Meaning                                                                                                                                                                                              |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `delivered` | The run was parked on `event_name`; the payload became its step result and the run is due now.                                                                                                       |
| `buffered`  | The run is not parked on `event_name`; the payload is stored in the run's inbox.                                                                                                                     |
| `duplicate` | The run already holds a value for `event_name`: a buffered signal, or a saved step named `event_name` (SDK waits use the event name as their step name). The first value wins; this one is not kept. |
| `finished`  | The run has finished. Nothing is stored.                                                                                                                                                             |
| `missing`   | No retained run has this ID. Nothing is stored.                                                                                                                                                      |

Run-addressed event names are 1–255 bytes without control characters. `WaitForEvent` consumes a buffered payload for its `event_name` in the same transaction that would park the run: the payload becomes the step result, the inbox entry is removed, the run is due now, and the reply is `{delivered: true}`. The worker loses its claim either way. The run's row lock (Postgres) or the write lock (SQLite) orders a signal with the wait, so a run-addressed signal is either delivered to a parked run or consumed by its next wait; it cannot fall between the two. Signals reach the inbox only after their transaction commits.

An inbox holds at most 1,000 entries and 8 MiB of payload JSON per run. A signal past either limit is rejected with `signal_inbox_full` and nothing is stored; delivery to a parked run needs no inbox room. Entries a run never consumes stay until the run is pruned with its history, so a reused run ID starts with an empty inbox. `GetWorkflowRun` lists the 100 oldest entries (name, receipt time, payload size) with the total count.

A wait whose deadline has passed is timed out: its step is `null`. What counts is when the value arrived, never how soon the run registers its wait or is claimed. A signal or awaited outcome that arrives after the deadline leaves the wait timed out, including one buffered (or a target that finished) after the deadline but before `WaitForEvent`/`WaitForRun` registers the wait; such a late buffered signal stays in the inbox unconsumed. A run-addressed signal that finds its wait already timed out reports `duplicate`.

A raw `WaitForEvent` whose `step_name` differs from its `event_name` saves the payload under `step_name`, so a later signal for the event is buffered for the next wait rather than reported as a duplicate. Step names starting with `__` are reserved for Tako's own checkpoints; SDK workers fail a run that uses one.

SDK workers save a wait's deadline as the step `__wait:<step_name>` (`{timeoutAt}` in Unix ms) before the first `WaitForEvent`, and reuse it on replay, so the timeout counts from the first time the run reached the wait.

## Workflow schedules

A starting worker sends `RegisterSchedules {app,build?,schedules}` with the complete set from every worker group. The build is the worker's `TAKO_BUILD`. Each installed runtime accepts its own build's first successful registration. An empty set removes every schedule. An explicit deployment or rollback to a shared Postgres store allocates a revision. The server commits that revision with the local release and Postgres checks it atomically with schedule replacement, including after server recovery.

Each `ScheduleSpec` is `{name,cron,max_attempts?}`. Five-field Unix cron runs in UTC with Sunday numbered 0 or 7. Seconds-first expressions with an optional year and the existing aliases use the Rust `cron` grammar. JavaScript sends `retries + 1` and Go sends `WithMaxAttempts` as the total attempt budget. The default is three attempts.

## Workflow run operations

Operators inspect and repair runs with four management commands: `ListWorkflowRuns {app,status?,name?,limit?}`, `GetWorkflowRun {app,id}`, `RetryWorkflowRun {app,id}`, and `CancelWorkflowRun {app,id}`. They are app-scoped like other application commands; list and get are read-only. The internal socket rejects them, so an app process cannot list or change runs, its own included. The worker's `CancelRun` is a different command: it carries the claim owner and ends the run from inside its handler.

Each server answers from the app's store as it sees it: its own SQLite file, or the Postgres store shared by every server of the app. Replies name the store (`sqlite` or `postgres`) so clients can tell one server's runs from a shared set. A stopped app's runs stay readable.

List returns the newest runs first, 50 by default and at most 200. Get returns every run field, the 100 most recent saved steps, the run's event waits, and its oldest 100 buffered signals with `signals_total`. Replies must fit one 1 MiB JSONL frame, so the server caps stored text: the payload and result at 32 KiB, each step result at 2 KiB, and errors at 8 KiB (1 KiB in lists). Workflow, step and event names and claim owners are cut to 256 bytes. A reply serializes to at most 768 KiB: a list stops early and sets `has_more`, and a run drops its oldest steps; waits and buffered signals are never dropped. A capped JSON value carries `truncated: true`, its stored size, and a UTF-8-safe text preview instead of the value. A run parked until a signal reports no due time.

Retry accepts only `dead` and `cancelled` runs. The run becomes `pending`, due now, with its attempts reset and its saved steps kept, so the handler resumes after its last checkpoint. Cancel accepts `pending` and `running` runs and removes their event waits. A running attempt loses its claim: its later heartbeats, checkpoints, and lifecycle writes are rejected with the same `run_not_owned` error as a reclaimed attempt's, and reclaim leaves the cancelled run alone. SDK workers treat that code on a worker write as lost ownership. They stop the attempt at its next checkpoint without failing, retrying, or completing the run; side effects already started are not undone.

## Ephemeral channels

Channel registry metadata, authorization responses, and internal publish lifecycle metadata carry optional `ephemeral: true`. Omission or false selects durable delivery. Ephemeral definitions omit `replayWindowMs`; supplying both is invalid. Durability is a definition setting and cannot be changed by client input or an authorization grant.

Ephemeral publication uses a bounded in-memory broadcast bus shared by handles for the same deployed app database path. Event allocation, local delivery and publication enqueueing share an in-memory order independent of the durable writer lock. Publishing and ingest do not access SQLite. `eventId.origin` is `live_` followed by a random 32-byte base64url incarnation, and `eventId.sequence` starts at one for that incarnation. Receiving handles remember at most 256 origins and their latest sequences in memory; repeats and older sequences are discarded while remembered, sequence gaps do not invalidate durable replay, and recreating the state forgets duplicate history. Ephemeral events have no lifecycle or creation timestamp for replay. Durable events retain their persisted origin, sequence and gap handling.

Native brokers forward local ephemeral events once to connected peers, regardless of local subscriber count; peers deliver locally without rebroadcasting. A connection-local identity on queued inbound commands rejects frames from an obsolete connection after peer replacement, in addition to membership-generation checks. Ephemeral broker commands, publication buffers, peer queues and proxy-notification queues are separate from durable traffic. Peer and notification queues reserve 64 packets and 2 MiB per receiver for each delivery class, with independent shared byte budgets; ephemeral overflow drops new events without evicting peers or fencing durable replay. A full ephemeral inbound command queue drops remote live events so subsequent durable/control frames can be admitted. Shared connection loss still fences durable replay.

Only active reachable subscriptions receive events; subscriber buffers hold 64 messages, lagging subscribers skip evicted events, and reconnects have no replay. Acceptance acknowledges local best-effort fanout, not remote/browser receipt. Per-origin order is preserved within an incarnation; concurrent origins have no total order. A lost publish acknowledgement is ambiguous, so retrying can create a second event. Applications tolerate loss and repeats and recover authoritative state independently. Ephemeral `ChannelMessage` values have an empty `id`; SSE frames omit the replay ID. Shared Postgres stores still reject ephemeral delivery, including with native networking configured. Local development reads the channel registry for params and the auth scheme and takes the delivery mode from the app's authorize answer, as production does.

## Channel streams

A channel stream is identified by the channel name and its validated params. Subscribers, WebSocket connections, client WebSocket publishes, replay, cursors, budgets, and fan-out are per stream, for durable and ephemeral channels, on one server and across the mesh or a shared Postgres store. Absent params and an empty object select the channel's single unparameterized stream. Presence keeps one transport stream per presence name; its membership is scoped by params separately.

SSE subscribe requests use `/_tako/channels/sse/<name>` and dedicated WebSocket connects use `/_tako/channels/ws/<name>`. A dedicated WebSocket accepts client frames (auth, presence updates and publishes) of at most 1 MiB, the event limit; the JavaScript SDK refuses a larger `send()`. These requests carry params as flat query pairs, excluding the reserved WebSocket cursor key `last_message_id`. The server coerces each value by the type its params schema declares for that property (`integer`, `number`, `boolean`; anything else stays a string) and validates the result against the schema, in production and local development. Each distinct param value selects a stream, so a param the schema does not declare under `properties` is rejected (`400`, `invalid channel params: unknown param '<name>'`, before authorization and before any stream bookkeeping) unless the schema explicitly sets `additionalProperties: true`, whatever JSON Schema's own default; a schema without properties accepts no params. A channel or presence params schema must be one object schema with its params under top-level `properties`: a schema that is not an object, has a `type` other than `object`, uses `$ref`, `$dynamicRef`, or `patternProperties` at the top level, or has a top-level combinator (`allOf`, `anyOf`, `oneOf`, `not`, `if`/`then`/`else`, `dependentSchemas`) one of whose subschemas, at any depth of nested combinators, names a param under `properties` that the top-level `properties` does not declare (the error names it), or declares `patternProperties`, `additionalProperties` other than `false`, `$ref`, or `$dynamicRef` fails every subscribe, connect, publish, and close with `invalid channel schema: ...` (a logged `500` on subscribe), and the JavaScript and Go definitions reject it when the channel is defined. A top-level combinator that only adds constraints over the declared params, such as `oneOf: [{ required: ["userId"] }, { required: ["teamId"] }]`, or `if: { properties: { kind: { const: "team" } } }, then: { required: ["teamId"] }` with `kind` and `teamId` declared, is allowed and enforced. The server checks every channel and presence params schema once when it loads a build's channel registry and logs a warning for each invalid one; the registry still loads. The reserved query keys below are not params and are unaffected. WebSocket requests are checked the same way before the upgrade. The JavaScript `defineChannel`/`definePresence`, Go `Channels.Register`, and Rust `PresenceDefinition` emit `additionalProperties: false` when no schema (or, in JavaScript, no explicit setting) is given; Store schemas are unchanged. Canonicalization matches Stores and presence: object keys are sorted, null entries are dropped, and integral numbers compare equal (`1` and `1.0`).

The internal `channel_publish` command is `{ "command": "channel_publish", "app", "channel", "params", "build", "payload" }`. `channel` is the public name. `params` is a JSON object, at most 16 KiB, or omitted/null for the unparameterized stream; values must have the types subscribers' query values are coerced to. A query cannot carry null, so a `null` param value is rejected (`channel param '<name>' is null`) rather than dropped: dropping it would select a different stream, the unparameterized one if it was the only param. `build` is the publisher's `TAKO_BUILD`. When the server has loaded the channel registry for that build, it rejects a channel that build does not define (`channel publish failed: bad request: channel '<name>' is not defined by build <build>`; the same for `channel_close`), validates `params` against the channel's params schema, including the undeclared-param rule, and rejects mismatches; without a loaded registry only the shape is checked; it never loads the registry for a publish. Stores ignore `params` and keep scoping invalidations by `payload.scopeParams`. The acknowledgement and every delivered `ChannelMessage` carry the public channel name; the internal stream key is never sent to clients or apps. Names starting with `tako.stream:` are reserved and rejected as routes and publish targets.

Channel params are flat scalars. The JavaScript SDK serializes each subscribe/connect param as a query value (dropping `undefined` and null, rejecting objects, arrays, and non-finite numbers) and, for a publish, sends what the server would bind for that query: each value is serialized the same way, then coerced by the definition's declared property type. A value a JavaScript number cannot carry exactly would bind different streams on the two sides, so with a definition the SDK rejects, when a handle is bound and again on subscribe, connect, publish, and close, an `integer` param that is not a safe integer (magnitude above 2^53 - 1, number, `bigint`, or numeric string) and a `number` param that is not finite (such as `1e400`). `channel_publish` omits `params` for the unparameterized stream and `build` when `TAKO_BUILD` is unset. A network `publish` request's `params` are validated against the recipient's definition and select the stream as a local publish does. Go has no server-side channel publish.

Replay cursors are opaque strings that name their stream (SQLite `s1.<epoch>.<stream>.<position>`, Postgres `p1.<stream>.<position>`), so a cursor from one params binding, or a bare numeric position, is stale on another stream and the client resets. Stream bookkeeping is released once a stream retains no messages and has had no activity for longer than its longest connection lifetime plus a grace period; a released stream restarts at the store's current head, so cursors from its earlier life reset. An app keeps bookkeeping for at most 100,000 streams (the default total replay message budget). Starting another stream derived from params (a channel stream or a Store scope) beyond that fails with a logged storage error (`500` for a subscribe, `channel publish failed: storage error: channel stream limit reached ...` for a publish); existing streams and unparameterized channel names are never refused, and a mesh event for a new stream at the limit is acknowledged and dropped: that server's readers of the stream never receive it, without a gap or reset, and the network agent logs a warning naming the app and the limit at most once a minute, with the number of events dropped. On shared Postgres, concurrent subscribers on several servers can overshoot the limit by the streams they start at once. Each store keeps a per-app stream count beside the metadata (SQLite in its state row, Postgres in `channel_stream_counts`, maintained by triggers in the same transaction), so the limit check reads one row however many streams exist. Maintenance runs every second with bounded work: age pruning visits at most 1,000 streams per tick, continuing after the last one next tick, and at most 1,000 idle streams are released per tick, both through indexes. Readers in both stores compute expired history themselves (rows older than the replay window, or every row of a stream idle past its inactivity TTL), so late pruning never serves expired messages or resumes an expired cursor. Shared Postgres stamps every message and stream activity, and judges every age (reader floors, pruning, idle release), by the database's clock, so servers whose clocks differ from it agree on what has expired.

Subscribe and connect requests may add the reserved query pair `from=start` to read every retained message of the stream instead of starting at its head. Any other `from` value is rejected with 400. An explicit cursor (`Last-Event-ID` for SSE; the `last_message_id` query or `tako.auth` `lastMessageId` for WebSocket) wins over `from`. If retention already dropped the beginning, the reader gets what is retained, without a reset. Ephemeral streams retain nothing, so `from=start` reads live messages only. `from` and `last_message_id` are never channel params: they are stripped from the params query (after percent-decoding), and publish or close params naming them are rejected.

The internal `channel_close` command is `{ "command": "channel_close", "app", "channel", "params", "build", "lifecycle" }`. `channel`, `params`, and `build` select and check the stream exactly as for `channel_publish`; `lifecycle` is the definition's lifecycle in the shape of a publish payload's `lifecycle` and may be omitted. It appends a durable terminal marker, a row of the reserved type `tako.close`, and replies `{ "id", "channel", "type": "tako.close", "data": null }` with the public channel name (`eventId` as for publish acknowledgements). Closing a closed stream succeeds and returns the existing marker. Ephemeral channels, Stores, and presence spaces cannot be closed (`channel close failed: bad request: ...`). While the marker is retained, `channel_publish` to that stream fails with `channel publish failed: channel stream is closed` and leaves the stream untouched (its lifecycle and activity time are applied only with an accepted append, so rejected publishes cannot keep an inactivity-TTL stream alive); no publish payload, server-side or WebSocket client, may use the type `tako.close`. The marker replicates over the mesh and through shared Postgres like a message, survives restarts, and is never delivered as an application message. Close wins on every SQLite node: once a stream has a retained marker, ingest acknowledges and drops any later event for it, a publish or a second marker, without storing or delivering it; the origin's sequence still advances, so the drop is no replication gap. The exception is an event made after the marker had expired, which the stream's own server accepted because it had reopened: each durable mesh event also carries `created_at_unix_ms`, the origin's creation time, every peer stamps its stored copy with it (so a message and a marker age out at the same moment on every node, whenever each one prunes), bounded by its own clock: a stamp is never later than the peer's current time, never more than 2 seconds earlier, and never earlier than the newest row already stored for that stream (or than the peer's current time, when that row is stamped later), so creation times grow with replay positions in every stream. A peer still holding a marker applies any later event from the server that made that marker: each server's events arrive in the order it made them, and it accepts publishes to the stream only once it has reopened it, however late its marker reached the peer. It applies an event from another server whose creation time as sent, capped at the peer's current time plus 2 seconds (so a fast clock cannot turn a publish that raced the close into a reopen), is later than the marker's stored stamp and at or past its expiry by the stream's replay window, the store age cap, or the inactivity TTL counted from the close, allowing 2 seconds of clock skew between servers; the marker counts as expired when it has under the window and TTL of the event's `lifecycle` (the definition its server used) or under the peer's stored ones, since a deploy that changed the window leaves the event's server judging its marker by either. It first deletes the marker and the closed history, as the reopened server did, which sets the stream's replay floor to the marker: a cursor below the marker gets the stale-cursor reset, while one exactly at it, whose reader already got the close, stays valid, as at the reopened server once its maintenance deleted the marker. An event without `created_at_unix_ms` keeps close-wins. A close is therefore ordered after its own server's earlier publishes, which reach peers first, while a publish from another server that races the close may be dropped (servers that applied it before the marker keep it). Shared Postgres takes publishes and closes under one per-app lock, so nothing races there. Each durable mesh event (`ChannelPublication::Event`) carries an optional `lifecycle` (`replayWindowMs`, `inactivityTtlMs`, `keepaliveIntervalMs`, `maxConnectionLifetimeMs`): the origin stream's lifecycle after the append. A peer creates or updates the stream with it, so a stream first seen through replication, and its marker, are retained as long as on the origin rather than under the default ten-minute window; an event without it keeps the peer's current lifecycle (the default for a new stream). Shared Postgres has one metadata row per stream that every server writes, so it needs no lifecycle in its wake hints. The closed state lasts as long as the stream's retained history: once retention deletes the marker the stream is open again, and an idle released stream starts fresh.

Readers receive every message before the marker, then the terminal signal, then the server ends the connection. SSE sends `id: <marker cursor>\nevent: tako.close\ndata: {}\n\n` and ends the response. WebSocket sends a close frame with code 4200 and reason `stream-closed` (`ChannelCloseCode::StreamClosed`, errkit code `SVUM3R`); a WebSocket client publish that races the close gets the same frame. A reader whose cursor is at or after the marker, or that connects at the head of a closed stream, receives the terminal signal at once; one connecting with `from=start` or an earlier cursor replays the retained messages first. The terminal signal is final: clients must not reconnect. `tako.reset`, close code 4410, a 1000 `connection expired` close, and an ended SSE response without `tako.close` remain reconnectable.

The JavaScript SDK's `channel(params).close()` sends `channel_close` with params normalized as for `channel_publish`, `build` when `TAKO_BUILD` is set, and the definition's lifecycle; params and build are omitted when empty or unset, as for publish. It rejects ephemeral definitions and runs only in the server runtime. Its `from: "start"` subscribe/connect option sends `from=start` only when no cursor is given. The SDK treats SSE `tako.close` and WebSocket 4200 as final, calling `close()` on a custom `EventSource`, and never delivers the marker as an application message. JavaScript `defineChannel` and Go `Channels.Register` reject channel and presence params schemas that declare `from` or `last_message_id`; Store params travel as JSON and are not affected. Go has no server-side channel publish or close, network `publish` has no close operation, and neither Go nor Rust has a channel subscribe client.

SQLite writer opens clamp previously stored future message and activity timestamps to the current local time, preserving message order and allowing old rows to age out without changing message IDs. On native networks the channel writer is the network agent's broker. It accepts lifecycle settings atomically with each publish; transport failures never select a weaker publish path. Server upgrades restart the running network agent and standby before releasing upgrade mode, including when the primary binary is already current.

### Shared WebSocket transport

`GET /_tako/channels/ws` upgrades to one multiplexed WebSocket per app/environment. The JavaScript SDK pools writable WebSocket channels and Presence by origin, normalized credentials, factory identity, and configuration generation within each tab. SSE subscriptions and Store notification streams keep their dedicated HTTP connections. `connection: "dedicated"` uses `/_tako/channels/ws/<name>`. SSE uses `/_tako/channels/sse/<name>`; the SSE path rejects WebSocket upgrades, and WS paths require an upgrade. Transport names are path namespaces, so channels named `ws` or `sse` remain valid.

Client JSON commands are `{ "type": "subscribe", "id", "channel", "query", "headers"?, "token"?, "cursor"?, "from"? }`, `{ "type": "unsubscribe", "id" }`, and `{ "type": "send", "id", "data" }`. `query` is the encoded params query. Each subscription resolves the current production app instance, then runs the existing `connect` authorization and params validation; a WebSocket grant is required, and Stores cannot join. Only the definition's declared auth header is read from `headers`; an optional `token` supplies that header when it is absent, matching dedicated `tako.auth` semantics for custom header names. Cookies, origin, and routing authority come from the physical handshake. Each subscription owns its replay cursor and presence membership. Unsubscribe cancels pending authorization and delivery and drops its presence session; the existing presence lease covers lost cleanup. Reused IDs cannot receive frames queued by an older subscription generation.

Presence cleanup completes any in-flight backend update before issuing removal, including cancellation during the first join. This prevents a successful delayed write from restoring a membership after cleanup; the lease still covers failed or lost cleanup.

The SDK's `resetChannelConnections()` closes all pooled subscriptions with retryable `1012` and advances the pool generation. Applications must call it after session cookies change on login/logout/account switching, before new subscriptions mount; HttpOnly changes cannot be detected automatically. Token-based account changes also require reset to retire existing subscriptions. `configureChannels` resets active pools after installing the new configuration. Pending token resolutions cannot join retired connections. React hooks reconnect; low-level callers own reconnection. Dedicated connections provide fresh handshakes when the application cannot integrate session reset.

Server commands are `{ "type": "subscribed", "id" }`, `{ "type": "unsubscribed", "id" }`, `{ "type": "data", "id", "data": "<JSON fragment>", "end": boolean }`, and `{ "type": "closed", "id", "code", "reason" }`. `subscribed` is sent only after the replay position and live watchers are installed. UTF-8 fragments are ordered within a subscription and can interleave across subscriptions; consumers deliver only complete messages. Logical close codes preserve `4200` (terminal stream), `4410` (reset), `4400`/`4401`/`4403`/`4404` (invalid request or authorization), `4429` (capacity), and `1009` (oversize). Closing one subscription does not close the socket. If the app authorize endpoint becomes unavailable (logical `1013`), the physical socket closes with `1012` so reconnection resolves the current app instance after a redeploy or scale-to-zero.

Limits: 32 subscriptions including pending auth, 64 KiB incoming command frames, 1 MiB complete delivered events, 8 KiB raw UTF-8 fragments, a 16-frame outgoing queue, and 16 pending publish commands per subscription. Shared replay reads one record at a time; bounded serialization stops above the message budget. Socket writes and auth time out after 10 seconds. If a terminal subscription frame cannot enter the bounded output queue before its deadline, a separate signal closes the physical connection with retryable `1012`; clients cannot remain attached to a silently ended subscription. Connection pings run every 25 seconds and expire after 75 seconds without client traffic. Large application records must be streamed as smaller events. No batching delay is added. React hooks reconnect independently; low-level `connect()` returns one logical socket whose owner handles reconnection. Releasing the last logical socket closes the physical connection after the current turn.

## Presence

JavaScript, Go, and Rust presence definitions use the channel registry and authorization endpoint, with wire names prefixed by `tako.presence:`. Channel and presence names therefore have separate namespaces. The connect authorization result supplies the trusted `subject`; it must succeed before the server creates a presence session or returns membership.

Presence uses the channel WebSocket route. After authorization, the server sends `{ "type": "tako.presence.ready" }`. The client then sends `{ "type": "tako.presence", "data": ... }` to join or replace its metadata. Client updates cannot choose a subject or connection ID. Metadata is JSON and is limited to 16 KiB.

Server snapshots are `{ "type": "tako.presence", "connectionId": "...", "members": [{ "connectionId": "...", "subject": "...", "data": ... }] }`; anonymous entries omit `subject`. These control frames have no replay ID and are never stored as channel messages. The React hook waits for `ready` before joining so its update cannot precede a browser's first-frame auth envelope.

Membership is scoped by deployed app/environment, wire name, and canonical validated params. Every authorized connection within one scope sees the same members. Params are serialized with recursively sorted object keys, then the wire name and params tuple is hashed with SHA-256 to produce a fixed-size storage key; query ordering does not create separate spaces. Each connection gets a server-generated ID, including separate tabs for one subject.

The client renews a 45-second lease with an update every 15 seconds. Disconnect cleanup removes its record; expiry covers network loss and process crashes. Snapshots poll shared state at approximately one-second intervals. SQLite and Postgres store leases separately from replay, with Postgres keyed by app ID for cross-server visibility. Postgres stamps, reads, and expires presence leases using the database clock, so skewed server clocks cannot hide live members or retain them indefinitely. Maintenance bounds old future-stamped leases to one normal lease. Local dev uses the same WebSocket session loop and an in-memory store, and authorizes connections through the app as production does.

## Stores

JavaScript, Go, and Rust store definitions reuse the channel registry and
authorization endpoint with `tako.store:` wire names. Public reads use
`GET /_tako/stores/<name>?params=<JSON-object>`; live subscriptions use the SSE
channel route with that prefixed name and the same `params` JSON query envelope.
The client URL-encodes the complete object, preserving arrays, objects, nulls,
and numeric/string distinctions. Store channels reject WebSocket/client publishing.
Both routes validate the decoded params object against the registered schema and independently
authorize the subscribe operation. Names use
`^[A-Za-z0-9][A-Za-z0-9._-]{0,255}$`; validated params are JSON objects capped at
16 KiB.

After authorization, the proxy calls `POST /stores/load` on the app's internal
host using the bootstrap token. The request is `{ "store": "<public-name>",
"params": {...}, "subject"?: "<verified-subject>" }`; the subject comes only
from authorization. The SDK responds with `{ "data": ..., "offline"?: {
"maxAgeMs": <positive-safe-integer>, "version": "<1–128-byte-string>" } }`.
Bodies and responses are capped at 1 MiB. Public responses are `no-store`; the
proxy never forwards the bootstrap token or private loader error details.
Loader data is sent only to its requesting reader.

The trusted internal `channel_publish` command publishes an invalidation to the
base `tako.store:<name>` with payload `{ "type": "tako.store.invalidate",
"data": {}, "scopeParams": {...} }`. The native transport derives an opaque
storage key from the wire name and canonical params using SHA-256; it normalizes
equivalent integral numeric values before hashing. Params are consumed as routing
metadata and never sent to subscribers. App/environment identity remains part of
the underlying channel store namespace. Publication affects exactly one params
scope; there is no wildcard invalidation.

Every SSE connection starts from the current notification cursor and sends
`{ "type": "tako.store.ready", "data": {} }` after its change watcher and
cursor are established. Subsequent notifications are
`{ "type": "tako.store.invalidate", "data": {} }`. Store frames carry no
client replay cursor. Clients reload after ready and invalidation, coalesce
notifications during loads, and reload again after reconnect; no snapshot or
intermediate database-state replay is promised.

Development uses the same Store validation and authorization as production,
with in-memory notification storage. Production uses existing channel storage;
cross-server notifications require shared Postgres. Invalidations omit lifecycle settings to preserve subscriber settings and include `build` when `TAKO_BUILD` is set. Store invalidation is
separate from the application database transaction. Durable commit-and-notify
requires an application-owned outbox.

Offline caching is a client concern gated by the response's opt-in policy and
an explicit client cache scope/version. The browser stores no credentials,
bounds persisted data, honors expiry, and purges the active result and cache
entry on authorization denial. Offline writes and conflict resolution are not
part of this protocol.

## Changing the protocol

Update the typed owner, every producer and consumer, and the serialization or integration tests in one change. Update this document only when a cross-component boundary or invariant changes. User-facing behavior belongs in the website docs and SDK READMEs.

The internal-socket commands the SDKs send, the replies they parse, and the bootstrap envelope have JSON fixtures in `test-support/wire/`. `tako-core` tests generate them from the typed owners; the JavaScript, Go, and Rust SDK tests check their request builders and reply parsers against the same files.

## Public development tunnels

The public tunnel relay (`tako-sh/tunnel`) and `tako-dev-server` negotiate
`tako-tunnel-v2` as their WebSocket subprotocol. Each binary WebSocket message is a
named MessagePack value; byte payloads use MessagePack binary values. The mirrored
`tunnel_wire.rs` files own this contract and must change together. The relay
rejects clients without the subprotocol with HTTP 426. There is no legacy fallback.

HTTP exchanges are `Request` → `Response` headers → `ResponseChunk`* →
`ResponseEnd`. `ResponseError` means the body was truncated; a dropped connection
also fails unfinished bodies. `Cancel` aborts the request task. Each response has
a 128 KiB byte credit window. Each chunk consumes `max(length, 1024)` credits to
bound tiny-frame overhead; the relay sends `ResponseCredit { id, bytes }` for
that amount when its downstream body is consumed. Both peers enforce the budget.
Chunks are at most 64 KiB and are flushed without batching SSE events.
Response headers have a 30-second deadline; body streaming has no total timeout.
Each session allows 32 HTTP requests and 32 WebSockets concurrently. Request
bodies remain buffered with a 2 MiB limit; WebSocket messages are limited to 1 MiB.
The relay admits requests before reading uploads, which must finish within 15
seconds. A relay-wide limit of 128 public HTTP requests and WebSockets also covers
pending uploads and streamed responses; unavailable capacity returns HTTP 503.

Registration challenges are opaque authenticated tokens with a five-minute
expiry. Clients sign the returned nonce unchanged. Only a successfully signed
registration consumes replay-cache space: up to 64 per SSH key fingerprint and
4,096 across the relay until expiry. A key's OpenSSH comment remains part of its
stable URL identity but does not change its quota principal.

WebSocket exchanges start with `WebSocketOpen` → `WebSocketResponse` (HTTP status
and headers). The relay waits up to 30 seconds before upgrading the browser and
uses only the subprotocol selected by the local app. Rejections preserve status
and end-to-end headers with an empty body; local connection failures return 502
and local handshake timeouts return 504. Success precedes all `WebSocketFrame`
messages; `WebSocketClose` cancels both pending handshakes and active sockets.

`Ping { nonce }` / `Pong { nonce }` provides application liveness every 25 seconds
with a 75-second acknowledgement deadline. Reconnects use bounded jitter and only
reset backoff after a stable connection. Session-owned tasks are aborted on every
exit, including cancellation of the session future.

Before merging paired changes, run `python3 scripts/test-conformance.py ../tako`
from the Tunnel checkout. It builds both real peers and checks registration,
HTTP/SSE, WebSockets, cancellation, replacement, and shutdown. Tunnel's CI can
also verify a selected Tako revision using its `tako_ref` workflow input.

## Hosted databases

A hosted database is a SQLite file that one server owns and serves. Its name (`^[a-z][a-z0-9_-]{0,62}$`) identifies it within the network. Network state holds two records per database at scope `tako/databases`: a `SecretKind::Database` record named by the database name whose JSON value is `{ name, server, generation, created_at_unix_secs }` (home server device ID and a random 32-hex generation chosen at creation), and a `SecretKind::DatabaseKey` record named `<name>.<generation>` holding the base64 AES-256 snapshot key. Members with any deployment permission may pull the scope and read `Database` records; only full members read `DatabaseKey` records, and only they publish either. Deletion publishes tombstones for both. `tako sqlite create` refuses a name with a live record. Publishing has no compare-and-swap, so concurrent creates of one name can both publish; because each key is addressed by its generation, the directory record that wins always has its key, and a create that sees another generation recorded after publishing undoes itself (its key record and its server copy). `tako.toml` binds database names per environment in `[envs.<env>].databases`; `[databases.<name>] { backup? }` only overrides the environment's `backup.storage`, and `id`, `server`, and `access` there are rejected. Every database is reachable from every server of its network.

The server stores databases at `<data_dir>/databases/<name>/database.sqlite` (owner-only directory) and serves them over Hrana HTTP (JSON): `POST /v2/pipeline` for `@libsql/client`, `POST /v3/pipeline` and `POST /v3/cursor` for `@tursodatabase/serverless`, plus `GET /v2`, `GET /v3`, and `GET /health`. Apps reach `127.0.0.1:9845`. Each binding gets a random bearer token, generated by the server, that maps to one app environment and one database; tokens stay stable while the binding names the same database on the same server, and a rollout accepts the old and new tokens until it commits. Streams expire after 10 seconds idle. Requests are bounded to 32 MiB and responses to 64 MiB, counted as encoded JSON. A request waits at most 30 seconds for one of the database's 32 request slots (`503` otherwise) and only then counts as active; its body must then arrive within 30 seconds (`408` otherwise), freeing the slot. A pipeline or cursor request holds at most 65,536 requests, batch steps, and condition terms together, counted while it is parsed (`400` otherwise). Statements longer than 4 KiB are prepared without the per-connection statement cache (32 entries). A server buffers at most 256 MiB of request bodies, pipeline results, and cursor output across every database: a request reserves its `Content-Length` (or 32 MiB without one; a larger declared length is answered `413` unread) before its body is read, waiting within the same 30 seconds as for a slot; a pipeline's results hold their bytes until the response has been sent, and a pipeline that finds none left stops, closes its stream, and is answered `503`; each queued cursor line counts at its full size. A database whose registration failed is retried every minute. When a server stops serving its databases (drain or reload), requests still waiting for a slot are refused rather than admitted. Its open connections close after their current request, a request whose stream it closed meanwhile gets `503` saying the transaction was rolled back, and a valid token for a database it no longer serves gets `503` (retry) rather than `401`. Queries and migrations from full clients wait for a request slot within the same 30-second admission timeout as app requests. Pruning also deletes snapshot data objects that have had no manifest for 24 hours (left by an interrupted upload or pruning). A deploy pins the databases it binds until it ends; `DeleteDatabase` refuses a pinned database, and a deploy refuses one being deleted. Native SDKs read the fd-3 bootstrap envelope before user code runs (Go at package init, JavaScript at import); the Rust SDK marks fd 3 close-on-exec from a static initializer before `main`, so subprocesses never inherit it. The Rust SDK reads the envelope on first use, so servers (and `tako dev`) do not wait for the whole envelope to be written before accepting readiness on fd 4: the rest is written as the app reads it, within the startup timeout until it is ready. A stream stores at most 256 SQL texts, 1 MiB in total, and every open stream of a server together at most 64 MiB (`SQL_STORE_LIMIT`). A named argument with a `:`, `@`, or `$` prefix binds exactly that parameter; a bare name binds whichever prefixed form the statement uses. Two arguments that bind the same parameter are rejected (`ARGS_INVALID`). Column names, error messages, and each result's fixed fields count against the response limit along with rows; a result past it becomes a `RESPONSE_TOO_LARGE` error. A cursor row larger than the response limit fails its step with `RESPONSE_TOO_LARGE`, and output the client has not read is held to 64 entries and 4 MiB (one larger row waits alone). A skipped batch step satisfies neither an `ok` nor an `error` condition. A cursor whose client stops reading for 30 seconds is stopped: its stream closes, its transaction rolls back, and the response ends with an error. A paused database answers `503`. Each listener holds at most 1,024 connections and accepts more as others close; a connection that sends no request headers within 30 seconds, first or between requests, is closed, as is one whose response makes no write progress for 30 seconds. Rows are sized from SQLite's values, and reserved against the response limit and the server's buffer, before they are copied. Pipeline and cursor output keeps its reservation until the connection has written it: each response chunk carries it, and the connection drops a chunk only after writing it. Each connection keeps at most 1 MiB of page cache (`cache_size` is not settable), and SQLite's memory in the server process has a 256 MiB soft limit past which page caches reuse pages instead of growing. Work directories of imports and exports are marked in use with each chunk, so the 24-hour cleanup of interrupted work leaves active transfers alone. A snapshot whose holder check passed re-checks after writing its manifest and deletes it if another server claimed the database meanwhile.

The engine connection is hardened: `ATTACH` (and so `VACUUM INTO`) is denied, `load_extension` and `fts3_tokenizer` are unavailable, only introspection, session, and `user_version`/`application_id`/`auto_vacuum` pragmas run, `foreign_keys` is on, `synchronous` is `FULL`, statements stop after 30 seconds, and writers wait up to 5 seconds for a lock. Each served file holds a shared lock on `<path>.lock`; replacing the file takes it exclusively.

`RunRelease.databases` and `Deploy.databases` carry `DatabaseBinding { name, server, peer_key? }` per binding; the CLI resolves each bound name's server from the network's `Database` records, and fails a deploy that binds a name the network lacks. The deploying server validates that local bindings name databases it hosts. Scoped deploys cannot change bindings. For a network binding, the app's server forwards to the home server's private address at port 9847 with `x-tako-database-scope` (app/environment, also for a release command's temporary bindings), `x-tako-database` (the database name), and `x-tako-database-key`. The network firewall accepts 9847 only from server peers. `GrantDatabases { app, databases, keep_existing }` sets an environment's grant on the home server, or with `keep_existing` adds to it, and returns its `peer_key`, which stays the same while the environment holds a grant; a full client's deploy puts it in `DatabaseBinding.peer_key`. A deploy only adds grants before its rollout, since the previous release keeps serving until it succeeds, and sets each home's exact grant once every server succeeded; a failed rollout leaves the wider grant. The home server accepts a forwarded request only from an effective server WireGuard address carrying the grant's key, so other processes on a granted server cannot act for the environment. Scoped deploys compare bindings without their keys, and the server fills a release command's keys from the provisioned bindings. Deleting a database revokes it from grants; bindings of apps on its own server block the delete. Tokens never leave the app's server.

Management commands name databases by `name`. `CreateDatabase { name, generation, backup_key_base64, backup? }` creates one; the others are `DeleteDatabase`, `DatabaseStatus`, `ConfigureDatabaseBackup`, `GrantDatabases`, `SnapshotDatabase`, `ListDatabaseSnapshots`, `RestoreDatabase`, `QueryDatabase` (at most 1,000 rows and 8 MiB, to fit the 16 MiB management relay), and the chunked transfers `BeginDatabaseImport`/`DatabaseImportChunk`/`FinishDatabaseImport` and `BeginDatabaseExport`/`DatabaseExportChunk`/`FinishDatabaseExport` (512 KiB base64 chunks, SHA-256 checked, sessions expire after an hour). They require full access, except `SnapshotDatabase` with `app` and reason `release`, which an app deployer may send for a database that app uses. A snapshot with reason `release` (the one before a release command) is skipped when the database is unchanged or has no backup destination; full clients send it without `app`, so a deploy that first binds a database can take it. `QueryDatabase` runs each statement in its own transaction and rejects one that would leave a transaction open. `MigrateDatabase { name, owner, migrations: [{ name, sql }], dry_run, app? }` applies pending migrations (file names `<number>[_<name>].sql`, ordered by number, numbers unique) and replies `{ applied, pending, warnings }`; it takes a snapshot with reason `migration` first when any are pending and backups are configured. Each file and its row in the database's `_tako_migrations (app, name, sha256, applied_at)` table, keyed by `owner`, commit in one `BEGIN IMMEDIATE` transaction with foreign keys off and `PRAGMA foreign_key_check` required to pass; the authorizer refuses transaction statements (`BEGIN`, `COMMIT`, `END`, `ROLLBACK`) in the file when they are prepared, so a refused file commits nothing; a recorded file whose SHA-256 differs fails the command, and a recorded file that is missing warns. With `app`, an app deployer sends it for a database its environment uses, and `owner` must be the app's name. `ResetDatabase { name, owner?, migrations }` replaces the database with an empty one through the same path as a restore; `migrations` (of `owner`) are applied to the empty file first, so the swap installs it with its schema and a failing migration leaves the database unchanged. `CreateDatabase` that fails after creating the file or its row removes both. `DeleteDatabase { name, generation?, keep_snapshots }` also deletes the database's snapshot objects, unless `keep_snapshots` is set, and replies with `warnings` when it cannot; with `generation`, it refuses a database of that name of another generation (one created again meanwhile), and the CLI removes the network record only while it still names that generation. Deleting snapshots deletes the generation's snapshots for every copy, also one a move left holding them, and leaves the prefix's `holder` naming no server, so a copy the delete could not reach publishes nothing when it returns. The CLI keeps them when it removes a copy that shares them with a database that lives on: the empty copy of a failed `restore --server`, and the old copy a move left behind (`delete --server`). After a move, the CLI clears the old copy's backup destination so it stops taking snapshots. `DatabaseInfo` carries the database's `generation`; a move that finds a copy of the same generation on its target resumes (configures its backup and restores again) instead of creating it, and refuses a different database of that name. `DeleteDatabase` with `keep_snapshots` releases this server's holder claim, so abandoning a move lets the named copy snapshot again; a full `tako sqlite delete` also removes same-generation copies on the network's other servers. A restore also records the restoring server in the snapshot prefix's `holder` object; a server that finds another server there publishes no snapshot (checked before copying and again before the manifest), so an old copy whose server was unreachable during the move stops on its own. Copies of replaced contents (reason `restore`) are not checked: latest restores skip them.

Snapshots are taken hourly when the database changed, before release commands, before pending migrations, before restores, imports, and resets, and on demand. A snapshot is `VACUUM INTO` a work file, an integrity check, SHA-256, zstd level 3, and AES-256-GCM with the record's key, uploaded to `_tako/databases/<name>/<generation>/snapshots/<snapshot-id>.sqlite.zst.enc` before its manifest `<snapshot-id>.json` (format 1, naming the database and generation, which a listing must match). The generation keeps a database created again under an earlier name away from that one's snapshots. Retention keeps the newest snapshot, every snapshot of the last 24 hours, and the newest per day for 7 days and per week for 4 weeks. A failed snapshot retries after 5 minutes. Restore and import verify the replacement first, then pause the database, copy the contents being replaced when they changed since the last snapshot, swap the file, resume, and upload that copy with reason `restore`; the replaced file is also kept as `previous.sqlite`. `RestoreDatabase` without a snapshot ID restores the newest snapshot whose reason is not `restore`. `BackupBinding` no longer selects database files; `TAKO_DATA_DIR` and `TAKO_SHARED_DATA_DIR` are plain file directories.

A server opens its databases and serves 127.0.0.1:9845 before it restores apps, applying each app's bindings before its processes start; resolving other servers' addresses, grants, the peer listener, and snapshots start once the private network is up. A process that exits stops serving databases (releasing their file locks) before its apps when a reloaded successor is ready, and after them otherwise.

`tako dev` and `tako run` serve bindings from `.tako/data/databases/<name>.sqlite` over the same protocol on a random loopback port, without consulting the network state. Dev registration carries `databases` as binding name → absolute file path; the daemon serves them for the registration and keeps their tokens across re-registration.

## Hosted KV stores

A KV store is a hosted database whose engine is `kv`: a redb file at `<data_dir>/databases/<name>/store.redb`, served over the Redis protocol (RESP2, or RESP3 after `HELLO 3`) instead of Hrana. KV stores share databases' records, names, grants, pins, and management commands: the `Database` record's JSON adds `"engine": "kv"` (absent for SQLite), `StoredDatabase` and `DatabaseInfo` carry `engine`, `CreateDatabase` takes `engine` (default `sqlite`; a KV store refuses `backup`), and `DatabaseBinding` adds `engine` (omitted for SQLite). A binding's engine must match the record's, and `same_target` compares it. Bindings of both engines share an app's one binding map on the server, so `[envs.<env>].databases` and `[envs.<env>].kv` may not reuse a binding name. Commands that only make sense for SQLite (`ConfigureDatabaseBackup`, `SnapshotDatabase`, `ListDatabaseSnapshots`, `RestoreDatabase`, `QueryDatabase`, `MigrateDatabase`, `ResetDatabase`, and the transfers) refuse a KV store; `QueryKv { name, args }` runs one command as a full client and replies with JSON (strings, `{"base64"}` for other bytes, integers, `null`, arrays, `[key, value]` pairs for maps, `{"error"}`). Deploys grant KV stores like databases but skip their backup configuration, release snapshots, and migrations.

Apps reach `127.0.0.1:9846` and authenticate with `AUTH <token>`, `AUTH <user> <token>`, or `HELLO <2|3> AUTH <user> <token>`; before that, only `AUTH`, `HELLO`, `QUIT`, and `RESET` run (`NOAUTH` otherwise). A connection re-resolves its token before each batch of commands: once the binding is revoked or points to another home, the next command fails and the connection closes. For a store on another server, the app's server connects to the home server's private address at port 9848, sends `TAKO-FORWARD <scope> <store> <grant-key> <protocol>` as its first command, and on `+OK` relays both directions unchanged (the command that authenticated is answered locally; commands pipelined after it are re-encoded and sent upstream). The home server accepts the handshake only from an effective server WireGuard address carrying the scope's grant key; `AUTH` on a relayed connection is answered `OK` without changing who it acts for. The relay checks its binding every 5 seconds and closes when it changed. The network firewall accepts 9848 only from server peers.

Each store has one writer thread: writes from every connection queue to it, and it applies up to 256 queued jobs in one redb transaction committed with `Durability::Immediate` before any of them is answered, so acknowledged writes are durable and concurrent writes share a flush. A batch that changes nothing aborts instead of committing. Reads run on read transactions on the blocking pool. One connection's consecutive store commands run as one batch, in order; a batch stops early once its replies exceed 8 MiB and the rest run in the next one. `MULTI`/`EXEC` sends the queued commands as one job: they run together with nothing between them, and `WATCH` compares each key's version (bumped on every change, absent for a missing or expired key) inside that job, answering a nil array when one changed. A key absent at `WATCH` has no version, so while any connection watches, the store remembers in memory when each key was last removed (and the last `FLUSHDB`), dropping what no active watch needs; a key absent then and at `EXEC` aborts the transaction if it was removed after the `WATCH`. Queuing only checks the command and its arity, as in Redis; option errors surface in the `EXEC` reply. Queued commands are limited to 32 MiB together, charged 64 bytes each beyond their arguments; past that, queuing fails and `EXEC` aborts. Once an `EXEC` reply reaches 64 MiB, or the room reserved for it (below), its later large replies become errors; every command still runs. Keys live in `keys` by `fnv1a64(key) || key` (the 64-bit hash never zero), which makes `SCAN` cursors that hash; a page ends at `COUNT` keys or before a key its reply has no room for (64 MiB, or the connection's reply room, below), and keeps going while keys share the last hash, so the cursor always advances. Hash fields live in `fields` by `u32be(len(key)) || key || fnv1a64(field) || field`, so `HSCAN` cursors are field hashes and its pages end the same way, or before a field whose value would take the reply past 64 MiB. Glob matching for `KEYS`, `SCAN`, and `HSCAN` spends at most 20 million steps per command (a class costs its length) and fails the command past that. Expiries in `expiry` by `expires_at_ms || key`, and totals in `meta`. Expired keys are invisible to reads; up to 32 are removed with each write batch and up to 10,000 every 250 ms. A store accounts 64 bytes plus twice the key per key, 32 bytes plus key and field per hash field, and the values; once it holds 1 GiB, commands that can add data get `OOM`, whatever their effect, as with Redis's `noeviction`. Keys and fields are limited to 64 KiB, values to 16 MiB, a command to 32 MiB counting 48 bytes per argument besides its bytes (the memory its parsed form takes), and a reply to 64 MiB. Before `AUTH` (or the peer handshake) a connection parses one command at a time, of at most 10 arguments and 16 KiB (Redis's `unauthenticated multibulk length` and `unauthenticated bulk length` errors), so it never draws on the shared budget. Connections hold 64 KiB of requests each, counting parsed arguments, and draw larger requests from a 256 MiB budget shared by the server, waiting up to 30 seconds; a reply that the client does not read for 30 seconds closes the connection. Replies have their own 256 MiB budget, so neither can starve the other: a connection buffers 64 KiB of replies without it, takes up to 1 MiB more before running commands when the budget has it free, and holds what it takes until the replies are sent. The store runs a connection's commands while their replies fit that room; a read whose reply does not fit is dropped, and a `GETDEL`, `GETEX` or `SET ... GET` is checked against the value before it runs, so the batch stops there without effect. The connection then sends what it has, waits up to 30 seconds for room for that reply, and runs the command again, or fails it with `ERR the server is short of reply buffer space; retry`. `EXEC` reserves room for the largest replies its commands could have (a value for each `GET`-like command, 64 MiB for one that lists keys or fields, 256 bytes for others, at most 64 MiB) before it runs, failing the same way. A relayed connection keeps its request budget until the requests it buffered have been sent to the other server. `COMMAND INFO` gives known commands Redis 7's ten-field entry (name, arity, flags, key positions, ACL categories, and empty tips, key specifications and subcommands) and nil for others. Each listener holds at most 4,096 connections. Stores open in redb's multi-writer mode, so a reloaded successor opens them while the old process drains; `close_all` closes their connections after the current batch. KV stores have no snapshots.

`tako dev` and `tako run` serve KV bindings from `.tako/data/kv/<name>.redb` over the same protocol on a random loopback port. Dev registration carries `kv` as binding name → absolute file path.

Development registration carries raw `ComposeConfig` plus `compose_default_host` and optional `compose_base_host`. The daemon applies development hostname defaults (HTTP apps only) and variant substitution, reloads `x-tako` metadata on restart, and replaces the route patterns and service ports after readiness. `sdk: true` services receive the production contract with development values: the dev app name, the registration's bootstrap token, `TAKO_BUILD=dev`, and a pinned socket under `{dev data dir}/runtime/compose/<project>` mounted at `/run/tako`. The override file under `.tako/compose/` references `${TAKO_DEV_BOOTSTRAP_DATA}`, which only the development Compose client's environment holds, so no secret value is written into the project. The daemon registers an external-worker workflow runtime for the group.
