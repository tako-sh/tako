**Code facts. Release, activation, and drain call paths.**

The server exposes these stages independently through shared commands. Sequencing belongs to the deploy caller.

1. `PrepareReleaseUpload` plans a managed path. Upload → [operations/release_artifacts.rs:102](/workspace/tako/tako-server/src/operations/release_artifacts.rs:102) extracts into a sibling temporary directory, links shared logs, and renames it into place. Existing release directories are reused. [archive.rs:3](/workspace/tako/tako-server/src/archive.rs:3) delegates archive safety to `tar::Archive::unpack`; no explicit expanded-size quota exists here.
2. `PrepareRelease` → [operations/releases.rs:61](/workspace/tako/tako-server/src/operations/releases.rs:61) validates path/protocol, provisions app isolation, and prepares runtime/dependencies using supplied secrets without persisting them. `PrepareDeploy` validates routes/SSL and stages provider credentials. `RunRelease` executes the release command under an app lock before activation.
3. `Deploy` → [operations/deploy.rs:40](/workspace/tako/tako-server/src/operations/deploy.rs:40) validates app/version/routes/path/protocol, resolves staged SSL, and acquires a per-app `try_lock`. Native deployment snapshots previous config/routes/credentials, updates credentials/config, registers routes, requests certificates, synchronizes workflows, and starts or rolls instances. New route metadata is installed before the native rollout completes; failure restores the previous snapshot when present.
4. `RollingUpdater::update` → [instances/rolling.rs:82](/workspace/tako/tako-server/src/instances/rolling.rs:82) allocates replacements with routing suppressed, spawns and waits for health, requires an 8-second stability window per batch, checks all replacements, enables routing, then drains old instances. Defaults are batch size 1, health timeout 30 seconds, drain timeout 30 seconds. Failed replacement health removes candidates and preserves old instances.
5. Native spawn uses bootstrap FD 3 and readiness FD 4, with loopback `HOST` and dynamic `PORT=0`. [spawner/mod.rs:108](/workspace/tako/tako-server/src/instances/spawner/mod.rs:108) applies one timeout to bootstrap/readiness and marks a completed handshake healthy. Ongoing health probes use the internal token. [readiness.rs:13](/workspace/tako/tako-server/src/instances/spawner/readiness.rs:13) parses the reported port.
6. Drain marks an instance `Draining`, removing it from the healthy selection list, then waits for in-flight requests or deadline. Counts start in upstream request filtering and end in proxy logging ([service/mod.rs:71](/workspace/tako/tako-server/src/proxy/service/mod.rs:71)). `Instance::kill` ultimately calls Tokio child `kill`, not a native graceful SIGTERM handshake ([instance.rs:317](/workspace/tako/tako-server/src/instances/instance.rs:317)). Scale-down uses a similar drain loop.
7. Success persists app/routes. `FinalizeRelease` separately checks active version, atomically replaces `current`, and prunes unprotected releases. SQLite restoration re-registers routes, reloads credentials, starts positive-minimum apps, and restores zero-minimum apps idle ([server_state.rs:741](/workspace/tako/tako-server/src/server_state.rs:741)). Native persistence errors are logged by `persist_app_state`; do not assume the whole native deployment is one durable transaction. Compose has a distinct pending-marker/atomic-commit recovery path.

Stop/delete/server shutdown differ from rolling drain. [operations/lifecycle.rs:9](/workspace/tako/tako-server/src/operations/lifecycle.rs:9) drains workflows for up to 120 seconds, then `AppManager::stop_app` marks instances draining and kills them without waiting on HTTP counts. Server shutdown uses the same immediate instance-stop pattern after workflow shutdown ([manager.rs:105](/workspace/tako/tako-server/src/instances/manager.rs:105)).

Reload is SIGHUP → spawn successor with the same arguments → successor signals readiness/SIGUSR1 → predecessor SIGTERM → runtime shutdown → Pingora graceful termination ([startup/signals.rs:12](/workspace/tako/tako-server/src/startup/signals.rs:12)). Pingora's configured graceful timeout is 5 seconds. Public ports share via reuseport; management HTTP instead waits for the predecessor's 9844 listener to exit. Standby skips HTTP management, and promotion starts the Unix management socket and ACME, not management HTTP ([startup/standby.rs:59](/workspace/tako/tako-server/src/startup/standby.rs:59)).

**Suggestions. Narrow integration seams and invariants.**

| Work | Suggested implementation boundary and required property |
| --- | --- |
| Native WireGuard | Add explicit server-owned network/peer state and a narrow privileged OS reconciler, connected through installer helpers and startup. Existing state-store schema/migration machinery is at [state_store/schema.rs:107](/workspace/tako/tako-server/src/state_store/schema.rs:107). Keep interface/key provisioning out of app spawn and proxy request code. Validate interface/address/peer inputs before invoking privileged commands. Keep private keys out of logs, app bootstrap, and agent responses; avoid granting the whole runtime `CAP_NET_ADMIN`. |
| Network startup/reload | Establish/reconcile the intended interface and assigned management address before advertising management readiness. Preserve installer checks that prevent public/wildcard management bindings. Make reconciliation idempotent and give overlapping predecessor/successor processes explicit ownership; predecessor drain must not remove the successor's shared network or peers. WireGuard peer membership alone must not grant management authority. |
| Scoped agent authorization | Introduce a verified principal/grant result before dispatch, with canonical app/environment and the agreed operation/route limits. Check every RPC plus the separate upload/log handlers. Default-deny server-wide upgrade, global listing, challenge injection, and credential administration unless explicitly granted. `PrepareRelease` and `RunRelease` execute code, so they need the same scope boundary as activation. Resolve bare-app versus `app/environment` identity deliberately before authorization. |
| HTTPS management ingress | Reuse the current operation handlers behind a dedicated management ingress branch/listener using the agreed endpoint. Intercept before ordinary app routing, redirects, cache/static/channel handlers, and upstream forwarding. Authenticate TLS/server identity, reserve management routing from app claims, and enforce the grant for upload metadata, logs, preparation, deploy, finalize, rollback, and cleanup. Do not expose the unrestricted 9844 API by merely reverse-proxying it. |
| Credential persistence | Add expiry/revocation checks and durable grant metadata in the protected server store. For opaque bearer tokens, persist a verifier/hash rather than plaintext. Keep network membership, SSH administrator enrollment, agent grants, and app internal health tokens separate. If extending signature framing, bind target/audience and operation explicitly; update producer/consumer together under protocol v0. |
| Route and artifact scope | `validate_deploy_routes` only checks nonempty routes and filesystem-safe certificate hosts ([release.rs:618](/workspace/tako/tako-server/src/release.rs:618)). Add ownership checks for exact/wildcard/path overlaps and reserved management hosts, under concurrency control, before cert issuance or mutation. App confinement checks at [release.rs:591](/workspace/tako/tako-server/src/release.rs:591) must remain. Add upload/expanded-size quotas and body deadlines appropriate for public HTTPS; the current upload bound is caller-declared size. |
| Lifecycle reuse | Carry any new ingress/network metadata through activation, failed-rollout restoration, persistence, restart, rollback, and delete. Attach shared network resources to their actual lifetime, not individual old instances. Preserve accepted-operation completion on disconnect. Treat workflow drain, HTTP request drain, proxy shutdown, and network teardown as separate lifetimes. |

Existing boundaries to preserve include owner-only management socket access, restricted root helpers, app-specific Unix identities/cgroups, cleared child environments, internal socket peer-UID checks, and loopback app upstreams. See [isolation.rs:27](/workspace/tako/tako-server/src/isolation.rs:27), [spawn_command.rs:130](/workspace/tako/tako-server/src/instances/spawner/spawn_command.rs:130), and [enqueue_socket.rs:327](/workspace/tako/tako-workflows/src/enqueue_socket.rs:327). These are implemented safeguards, not a claim of complete network isolation. Protocol `force` bypasses version gates, not authorization or validation; keep that separation.
