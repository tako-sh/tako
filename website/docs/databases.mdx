description: "Create Tako-hosted SQLite databases on a network server, bind them to apps, query them with libSQL drivers, and back them up with encrypted snapshots."
---

A Tako database is a SQLite database that `tako-server` hosts on one server of a [native network](/networks/). Apps do not open the file. They reach it over the libSQL HTTP protocol (Hrana over HTTP, JSON encoding) with a per-binding token, so existing libSQL drivers work unchanged, the same code runs under `tako dev`, and Tako can snapshot, restore, and move the file without coordinating with app processes.

Use a hosted database for application data. `TAKO_DATA_DIR` and `TAKO_SHARED_DATA_DIR` remain plain file directories; Tako does not discover, capture, or back up SQLite files placed there.

| Need                                              | Use                                                     |
| ------------------------------------------------- | ------------------------------------------------------- |
| Relational app data that must survive server loss | A hosted database with a backup storage                 |
| Data shared by apps on several servers            | A hosted database with network access                   |
| Files, caches, or scratch data on one server      | `tako.dataDir` / `TAKO_DATA_DIR` ([Storage](/storage/)) |
| Postgres, MySQL, or another external database     | A [secret](/secrets/) holding its URL                   |

## Create a database

Databases live on native network servers, so the environment needs `[envs.<env>].network`. Creating one requires network and server administrator permission:

```bash
tako sqlite create main --env production --server edge-a
```

`create` makes the database file on `edge-a`, records the database in the network's encrypted shared state, and binds it in `tako.toml`:

```toml
[envs.production]
databases = { main = "main" }
```

The name identifies the database: names are unique within a network, and the network's records hold where each database lives and who may use it, so `tako.toml` only binds databases by name. Names start with a lowercase letter and contain lowercase letters, digits, `-`, and `_` (at most 63 characters).

`--server` can be omitted when the environment deploys to exactly one server. `--binding` chooses the app-facing name (it defaults to the database name). `--access network` lets apps on other servers use it (see [Share a database across servers](#share-a-database-across-servers)). Snapshots go to the environment's `backup.storage`; `--backup` chooses another private S3 storage resource and writes it to `[databases.<name>].backup`. Without either, `create` warns that the database has no snapshots. See [Back up and restore](#back-up-and-restore). Deploy to start using the binding:

```bash
tako deploy --env production
```

To use a database that already exists in the network from another project or environment, bind it by name:

```bash
tako sqlite link main --env staging --binding main
tako sqlite list --json
```

`list` shows every database recorded in the network, its server and access, and whether this project binds it (`in_project`). A deploy resolves each bound name in the network's records and fails when the network has no database with that name.

Each environment can bind a different database under the same name, such as `main = "shop"` in production and `main = "shop_staging"` in staging; app code reads the binding name. When an environment lacks a binding name that another environment has, `tako deploy` warns, since that database is missing when the app runs there. Development is checked only when `[envs.development].databases` is set.

## Use it from application code

Each binding is a connection: a URL on the app's own server plus a token for that binding. Pass it to a libSQL driver.

<CodeGroup>

```ts JavaScript
import { createClient } from "@libsql/client";
import { tako } from "tako.sh";

const main = tako.databases.main;
if (!main) throw new Error("No database is bound as main");

// `{ url, authToken }` is exactly what createClient expects.
const db = createClient(main);
const { rows } = await db.execute({
  sql: "SELECT id, email FROM users WHERE id = ?",
  args: [userId],
});
```

```go Go
package main

import (
	"database/sql"
	"log"

	_ "github.com/tursodatabase/libsql-client-go/libsql"
	"tako.sh"
)

func openMain() *sql.DB {
	main, ok := tako.GetDatabase("main")
	if !ok {
		log.Fatal("no database is bound as main")
	}
	// DSN() is the URL with the token as its authToken parameter.
	db, err := sql.Open("libsql", main.DSN())
	if err != nil {
		log.Fatal(err)
	}
	return db
}
```

```rust Rust
fn main_database() -> tako::Database {
    let main = tako::database("main").expect("a database bound as main");
    // Pass main.url() and main.auth_token() to a libSQL HTTP client.
    main
}
```

</CodeGroup>

JavaScript also works with `connect` from `@tursodatabase/serverless`, which uses the v3 cursor endpoint for streaming large results. Tako's test suite exercises both JavaScript drivers: statements, positional and named arguments, blobs, 64-bit integers, batches, interactive transactions, `executeMultiple`, cursors, and error codes.

`tako generate` adds a `TakoDatabases` interface to `tako.d.ts`, so `tako.databases.main` is typed for every bound name. Bindings are read when accessed. Logging or serializing a connection redacts its token; treat the token as a secret and never send it to a browser.

Go uses `tako.GetDatabase(name)` and `tako.DatabaseNames()`. `Database.DSN()` targets the `libsql` driver from `libsql-client-go`; formatting a `Database` with `%v` or `%#v` redacts the token. Rust uses `tako::database(name)`, returning `Option<tako::Database>` with `url()` and `auth_token()`; its `Debug` output redacts the token. Tako's test suite runs the Go SDK with `libsql-client-go` (statements, blobs, transactions, and errors); no Rust driver is part of it. Use one that speaks Hrana over HTTP with JSON; clients that require the protobuf encoding are not supported.

### ORMs

ORMs that run on `@libsql/client` reach Tako through it:

- Drizzle: `drizzle(createClient(tako.databases.main))` from `drizzle-orm/libsql`, with `migrate` from `drizzle-orm/libsql/migrator` for migrations run by app code.
- Prisma: `@prisma/adapter-libsql` with the same `url` and `authToken`. Prisma Migrate cannot open a Tako database directly; generate SQL (for example with `prisma migrate diff --script`) and apply it from a script.

Tako's test suite applies Drizzle migrations with `migrate` and queries through Drizzle, including a rolled-back transaction and a cascading delete; Prisma is not part of it. Migration tools that connect from your workstation cannot reach the database: the endpoint listens on the server's loopback interface. Run migrations as a [release command](/deployment/#release-commands) or through `tako run` in development.

## Develop locally

`tako dev` and `tako run` serve bound databases from local files with the same protocol and SDK surface, so code does not change between development and production:

```text
.tako/data/databases/<database-name>.sqlite
```

Files are created on first use. Development uses `[envs.development].databases` when it is set. Otherwise it binds every name used by any environment, taking the database from the first environment in name order, so most projects need no development bindings. To choose them yourself:

```toml
[envs.development]
databases = { main = "main" }
```

Run one-off scripts, such as migrations, with the app's bindings:

```bash
tako run bun scripts/migrate.ts
```

`tako run` always runs locally and serves only development bindings. With `--env production` (or any other environment) the script gets no databases and Tako prints a warning: hosted databases are reachable only from deployed apps. Use `tako sqlite shell`, `tako sqlite export`, or a release command for production data.

The development endpoint listens on a random loopback port for the lifetime of the dev daemon or `tako run`. Its URL and token change between sessions; read them from the binding rather than copying them.

## Query and inspect

```bash
tako sqlite status main --env production --json
tako sqlite shell main "SELECT count(*) FROM users" --env production --json
tako sqlite shell main --env production
```

`status` reports the size, the app environments using the database on its server (`bindings`), those granted from other servers (`remote_grants`), and backup state: destination, last snapshot, last attempt, and last error. Without a name it reports every database the environment binds.

`shell` runs SQL with an administrator connection. With SQL as an argument it runs that statement and exits; with `--json` it prints `columns`, `rows`, `affected_row_count`, and `truncated`. Results stop at 1,000 rows. Each statement commits on its own: `BEGIN` is rejected rather than silently leaving later statements outside a transaction, so run multi-statement changes from a script with a driver. Without SQL it reads statements from standard input; an interactive terminal also accepts `.tables`, `.schema [table]`, and `.quit`. The shell has the same restrictions as apps.

## Back up and restore

Snapshots go to a private S3-compatible storage resource (no `public_base_url`): the environment's `backup.storage`, or `[databases.<name>].backup` when set:

```toml
[envs.production]
databases = { main = "main" }
backup = { storage = "private_backups" }

# Only to use another storage for one database:
# [databases.main]
# backup = "other_backups"

[storages.private_backups]
provider = "s3"
bucket = "app-backups"
endpoint = "https://example.r2.cloudflarestorage.com"
region = "auto"
```

```bash
tako storages credentials private_backups --env production
tako deploy --env production
```

A deploy by an administrator sends the destination and credentials to the database's server; removing the backup storage and deploying stops snapshots, and moving it to another storage snapshots the database there on the next scheduler pass. Without a backup storage, Tako takes no snapshots and a lost server loses the database. Environments that bind the same database should use the same storage, since each administrator's deploy sets it.

The server then takes snapshots:

- every hour while the database changes; an unchanged database uploads nothing,
- before a deploy's release command, when the database changed since the last snapshot,
- before a restore or import replaces the database,
- on demand with `tako sqlite backup <name>`.

A snapshot is a consistent copy (`VACUUM INTO`) that passes `PRAGMA integrity_check`, compressed with zstd and encrypted with AES-256-GCM using the database's own key. The key is generated at `create` and kept in the network's encrypted shared state, readable only by administrators. Objects are written under `_tako/databases/<name>/<generation>/snapshots/`, where the generation is a random ID chosen at `create`, so a database created again under an earlier one's name never sees its snapshots. The manifest is written last, so only complete snapshots are listed. A failed snapshot is retried after five minutes.

Retention keeps every snapshot of the last 24 hours (so a release or manual snapshot survives the hourly ones after it), then the newest of each day for 7 days and of each week for 4 weeks. Recovery is to a snapshot, not to an arbitrary point in time: up to an hour of writes can be lost with the server.

```bash
tako sqlite backups main --env production --json
tako sqlite restore main --latest --env production
tako sqlite restore main --snapshot <snapshot-id> --env production
```

A restore downloads the snapshot and verifies its checksum and integrity before anything changes, then pauses the database, copies exactly the contents it replaces, and swaps the snapshot in. While a database is replaced, apps' requests to it get `503` responses. In-flight requests finish first; the replacement fails, leaving the database unchanged, if they take longer than 30 seconds. The replaced contents are uploaded as a snapshot with reason `restore` and kept beside the database as `previous.sqlite` until the next replacement. Writes since the restored snapshot are lost.

`--latest` restores the newest snapshot that is not one of these `restore` safety copies, so repeating a restore does not undo it. To go back to the contents a restore replaced, pass its `--snapshot` ID.

### Import and export

```bash
tako sqlite export main ./main.sqlite --env production
tako sqlite import main ./main.sqlite --env production
```

`export` downloads a consistent copy without pausing apps. `import` replaces the database with a local SQLite file after verifying it on the server; a snapshot of the current contents is taken first when backups are configured. Only the main file is uploaded: stop writers and checkpoint the file (`PRAGMA wal_checkpoint(TRUNCATE)`) before importing a database that uses WAL. Imports are limited to 64 GiB.

To move an app from a SQLite file in its data directory, create a hosted database, copy the file to your machine during a write freeze, import it, bind the database, and deploy the code that uses `tako.databases`.

### Recover on another server

```bash
tako sqlite restore main --latest --server edge-b --env production
tako deploy --env production
```

With `--server`, Tako creates the database on `edge-b` from its snapshot and records `edge-b` as its server in the network; `tako.toml` does not change. Deploy every app that binds it afterwards. Recovery requires a backup storage.

## Share a database across servers

By default (local access), only apps on the database's server may use it, and a deploy fails when the environment also targets other servers. Pass `--access network` to `create`, or change an existing database, to let apps on any server of the network use it:

```bash
tako sqlite access main network --env production
tako deploy --env production
```

The access is recorded in the network; deploy the apps that bind the database to apply it.

An app on another server connects to its own server as usual. That server forwards the request over the network's private WireGuard transport to the database's server on port 9847, which the network firewall opens only to other servers. An administrator's deploy grants the app environment the database on its server; the grant comes with a key that the deploy hands to the app's servers, and forwarded requests must carry it, so other processes on a granted server cannot act for the environment. Tokens never leave the app's server. A deploy without administration keeps the bindings and keys an administrator provisioned. Each remote query adds a private-network round trip, and the database is unavailable to every server while its home server is down; forwarded requests then fail with `502`. Writes are serialized on one server: there is no replication or failover.

## Limits and security

- Each binding has its own random token. A token works only on the server that issued it and only for the databases its app environment binds. Binding tokens stay stable across deploys while a binding names the same database.
- During a rolling deploy, the old and new release's bindings are both active, so old instances keep working until they drain. A release command receives temporary bindings that are revoked when it finishes.
- SQL cannot reach other files or load code: `ATTACH` (including `VACUUM INTO '<path>'`), `load_extension`, and `fts3_tokenizer` are refused. Plain `VACUUM` works.
- Reading any `PRAGMA` is allowed. Connection settings such as `foreign_keys` and `defer_foreign_keys` can be changed, as can `user_version`, `application_id`, and `auto_vacuum`. Other writes, such as `journal_mode` or `synchronous`, are refused: Tako runs WAL with `synchronous = FULL`.
- `foreign_keys` is on for every connection. A statement may run for at most 30 seconds and waits up to 5 seconds for the write lock. Interactive transactions idle for 10 seconds are rolled back.
- Requests are limited to 32 MiB and responses to 64 MiB. Use a cursor (`@tursodatabase/serverless` `iterate`) or pagination for larger results.
- Database bindings are available to native releases. [Container and Compose releases](/docker/) cannot use them yet.
- A scoped deploy client cannot change an environment's database bindings; an administrator must deploy the change.
- Managing databases (`create`, `access`, `status`, `shell`, `backup`, `backups`, `restore`, `import`, `export`, `delete`) requires network and server administrator permission. Every member that may deploy can read where databases live (`list`, `link`, and deploys); snapshot keys are readable only by administrators.
- `create` refuses a name the network already has. Two administrators creating the same name at the same moment are not detected; the later record wins.

## Delete a database

```bash
tako sqlite delete main --env production
```

`delete` (alias `rm`) removes the file from its server, the network records, and the database's bindings and `[databases.<name>]` settings from `tako.toml`. Snapshots stay in backup storage. Remove the code that uses the binding and deploy first: a deploy that still binds a deleted database fails. Apps on the database's server that still bind it block the delete. Grants to app environments on other servers are revoked, since they can outlive the deployments that used them; `delete` names those environments before asking to confirm.

## Verify

1. Run `tako sqlite status <name> --json` and confirm the server, `bindings` or `remote_grants`, and `backup.last_snapshot`.
2. Run `tako sqlite shell <name> "SELECT count(*) FROM <table>" --json` to check known rows.
3. Take a snapshot with `tako sqlite backup <name>` and list it with `tako sqlite backups <name>`.
4. Before depending on backups, restore a snapshot into a staging database or export one and open it locally.
