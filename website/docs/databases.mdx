---

Tako runs the Turso SQL engine on the servers selected by an environment’s deploy. Applications use a libSQL-compatible HTTP driver through the Tako binding. Each database has one elected writer. On that server, independent `BEGIN CONCURRENT` transactions can update different rows. Conflicting transactions can return `SQLITE_BUSY` and require a retry of the whole transaction.

Hosted databases use ordinary rowid tables. Use a primary key or a unique constraint for composite keys and omit `WITHOUT ROWID` from hosted migrations. Local development and portable SQLite imports and exports use SQLite.

Use a hosted database for application data. `TAKO_DATA_DIR` and `TAKO_SHARED_DATA_DIR` remain plain file directories; Tako does not discover, capture, or back up SQLite files placed there.

| Need                                                | Use                                                     |
| --------------------------------------------------- | ------------------------------------------------------- |
| Relational app data that must survive server loss   | A hosted database with a backup storage                 |
| Data shared by apps on several servers              | A hosted database                                       |
| Short-lived keys every server must see, with expiry | A [KV store](/kv/) of JSON values                       |
| Files, caches, or scratch data on one server        | `tako.dataDir` / `TAKO_DATA_DIR` ([Storage](/storage/)) |
| Postgres, MySQL, or another external database       | A [secret](/secrets/) holding its URL                   |

## Create and bind a database

Database names are unique across a network’s databases and KV stores. A name starts with a lowercase letter and contains up to 63 lowercase letters, digits, hyphens, or underscores. Declare the database under the environment in `tako.toml`. The key is the binding name in application code and the value is the database name.

```toml
[envs.production]
db = { main = "main" }
```

Then deploy with `tako deploy --env production`.

A full-access deploy claims each missing name and prepares a replica on each selected server. A second app using the same name joins the same database. Adding a server to the network alone does not copy app data. Deploy with full access when introducing a binding or a new target. Preparing reports storage readiness per binding before the rollout.

A deploy fails when a bound name belongs to a KV store rather than a database. `tako db list --json` shows the network's databases, their servers, and whether this project uses them (`in_project`).

Each environment can bind a different database under the same name, such as `main = "shop"` in production and `main = "shop_staging"` in staging; app code reads the binding name. An environment's `db` and `kv` bindings share one set of names, so a binding name is used by one of them. When an environment lacks a binding name that another environment has, `tako deploy` warns, since that database is missing when the app runs there. Development is checked only when `[envs.development].db` is set.

`tako db` commands use `--network` when given, else the network configured in the selected TOML file's environments, else this machine's only network, else they ask in an interactive terminal. When the environments configure several networks, pass `--network <alias-or-id>`.

#### Read from the local database

Pass `tako.db.main.readReplica` to the same libSQL client as `tako.db.main`. SQLite opens the local file read-only and rejects writes to it with `SQLITE_READONLY`. Interactive read transactions use the same connection for their lifetime. Go exposes `db.ReadReplica()` and Rust exposes `db.read_replica()`.

The ordinary binding sends reads and writes to the elected leader. A successful write is durable on a voting majority. One voter commits locally, two require both, and three require two. With one voter in each of three regions, a healthy write pays the round trip to the fastest acknowledging follower, plus a round trip from the app to the leader if they run apart. An election or loss of quorum can delay requests. The read replica serves the last locally applied transaction. It can lag a successful write. Use the ordinary binding for read-after-write consistency.

## Use a database for channel replay

`[envs.production.channels]` with `database = "chat-prod-replay"` selects a database for Tako to use on behalf of the app. It does **not** create an app SQL alias, run the project's SQL migrations against a replay-only database, or give the app, its workers or its release command a SQL token for replay. The same setting works for an SDK-enabled Compose group, which cannot use ordinary app SQL bindings.

Without that setting, a channel-capable deploy selects a generated app/environment database. The automatically owned database cannot be bound as app SQL. If you intentionally select an ordinary database for replay and also bind it for SQL, the SQL binding can read or change **every table**: channel namespace isolation is not a SQL access restriction. Prefer a dedicated replay database.

`tako db list --json` shows the home, `in_project`, `channel_replay_envs`, and `channel_owner` for an automatically owned database. `tako db status <name> --json` shows actual local bindings and remote grants; `<app>/<env>#channels` identifies runtime use, distinct from `<app>/<env>` for app SQL. For provider selection, multi-server placement, and upgrading existing apps, see [Deploy Replay Storage](/channels/#deploy-replay-storage).

## Use it from application code

Each binding is a connection: a URL on the app's own server plus a token for that binding. Pass it to a libSQL driver.

<CodeGroup>

```ts JavaScript
import { createClient } from "@libsql/client";
import { tako } from "tako.sh";

const main = tako.db.main;
if (!main) throw new Error("No database is bound as main");

// `{ url, authToken }` is exactly what createClient expects.
const db = createClient(main);
const { rows } = await db.execute({
  sql: "SELECT id, email FROM users WHERE id = ?",
  args: [userId],
});
```

```go Go
package main

import (
	"database/sql"
	"log"

	_ "github.com/tursodatabase/libsql-client-go/libsql"
	"tako.sh"
)

func openMain() *sql.DB {
	main, ok := tako.GetDB("main")
	if !ok {
		log.Fatal("no database is bound as main")
	}
	// DSN() is the URL with the token as its authToken parameter.
	db, err := sql.Open("libsql", main.DSN())
	if err != nil {
		log.Fatal(err)
	}
	return db
}
```

```rust Rust
fn main_database() -> tako::Db {
    let main = tako::db("main").expect("a database bound as main");
    // Pass main.url() and main.auth_token() to a libSQL HTTP client.
    main
}
```

</CodeGroup>

JavaScript also works with `connect` from `@tursodatabase/serverless`, which uses the v3 cursor endpoint for streaming large results. Tako's test suite exercises both JavaScript drivers: statements, positional and named arguments, blobs, 64-bit integers, batches, interactive transactions, `executeMultiple`, cursors, and error codes.

`tako generate` adds a `TakoDb` interface to `tako.d.ts`, so `tako.db.main` is typed for every bound name. Bindings are read when accessed. Logging or serializing a connection redacts its token; treat the token as a secret and never send it to a browser.

Go uses `tako.GetDB(name)` and `tako.DBNames()`. `DB.DSN()` targets the `libsql` driver from `libsql-client-go`; formatting a `DB` with `%v` or `%#v`, or encoding it with `encoding/json`, redacts the token. Rust uses `tako::db(name)`, returning `Option<tako::Db>` with `url()` and `auth_token()`; its `Debug` output redacts the token. Tako's test suite runs the Go SDK with `libsql-client-go` (statements, blobs, transactions, and errors); no Rust driver is part of it. Use one that speaks Hrana over HTTP with JSON; clients that require the protobuf encoding are not supported.

### ORMs

ORMs that run on `@libsql/client` reach Tako through it:

- Drizzle: `drizzle(createClient(tako.db.main))` from `drizzle-orm/libsql`, with `migrate` from `drizzle-orm/libsql/migrator` for migrations run by app code.
- Prisma: `@prisma/adapter-libsql` with the same `url` and `authToken`. Prisma Migrate cannot open a Tako database directly; generate SQL (for example with `prisma migrate diff --script`) into a [migration file](#migrations).

Tako's test suite applies Drizzle migrations with `migrate` and queries through Drizzle, including a rolled-back transaction and a cascading delete; Prisma is not part of it. Migration tools that connect from your workstation cannot reach the database: the endpoint listens on the server's loopback interface. Use [Tako's migrations](#migrations), or run a tool's migrator as a [release command](/deployment/#release-commands) or through `tako run` in development.

## Migrations

Put SQL files in `migrations/`, named with an order number, and create new ones with `migration new`, which prefixes the current UTC time:

```bash
tako db migration new "add orders"
# Created migrations/20261116143000_add_orders.sql
```

```text
migrations/
  0001_initial.sql
  20261116143000_add_orders.sql
```

Any number works as a prefix, up to 18 digits; files run in numeric order, so dated files sort after `0001`-style ones. When the project binds more than one database name, give each binding its own folder, `migrations/<binding>/…`, and pass `--binding` to `migration new`; loose files in `migrations/` are then an error, as they are next to a binding's own folder. Two files with one number are rejected, and other file types in the folder are ignored. One binding's migrations are sent to the server in one request, so together they may take at most 960 KiB as JSON; load large data with `tako db import` instead, or replace files every database has applied with one smaller file that is safe to run again (such as `CREATE TABLE IF NOT EXISTS`), numbered after them.

Tako applies pending migrations:

- on `tako deploy`, on the database's server, after the restore point before the release command and before the release command and rollout. A failing migration stops the deploy before any new instance starts. The previous release keeps serving while migrations run, so keep them compatible with it (add a column before code depends on it; drop it in a later deploy).
- in `tako dev` (before the app starts, on each reload, and whenever a file in `migrations/` is added or saved, without restarting the app) and `tako run`, on the local file.
- on `tako db migration apply [<database>]`. `migration list [<database>]` shows what is pending without applying it. Both act on every database the project binds by default; `--local` acts on the development files.

Each file runs in one `BEGIN IMMEDIATE` transaction together with its record in the database's `_tako_migrations` table (`app`, `name`, `sha256`, `applied_at`), so a failing file leaves nothing behind and the files before it stay applied. A file that contains `BEGIN`, `COMMIT`, `END`, or `ROLLBACK` is refused before that statement runs, and nothing in it is committed; `SAVEPOINT` and `RELEASE` work inside the file's transaction. Foreign keys are not enforced while a file runs, so it can rebuild a table that others reference ([SQLite's 12 steps](https://sqlite.org/lang_altertable.html#otheralter)), but `PRAGMA foreign_key_check` must pass before it commits. Statements have the same 30-second limit and restrictions as app queries. When backups are configured and something is pending, the server first uploads everything captured so far and records a restore point (reason `migration`) that names the state before the migrations. The previous release keeps serving meanwhile, so restoring that point also undoes its writes after it.

An applied migration must not change: a file whose contents differ from what was applied stops the deploy (or `tako dev`); restore it and put the change in a new file. A file that was applied and then deleted produces a warning. To squash old migrations once every database has them, replace them with one file that is safe to run again, numbered after them: databases that have the old files run it without changes, and new ones get their schema from it. A new file numbered below the latest applied one runs, with a warning. There are no down migrations; write a new migration that undoes the change, or [restore the point before it](#back-up-and-restore).

History is kept per app: apps that share a database each track their own migrations, so both can have a `0001_initial.sql`. Prefer letting one app own a shared database's schema. Within one app, a database bound under two binding names takes its migrations from one folder: two folders with different files for the same database are an error.

## Develop locally

`tako dev` and `tako run` serve bound databases from local files with the same protocol and SDK surface, so code does not change between development and production:

```text
.tako/data/databases/<database-name>.sqlite
```

Files are created on first use, and migrations are applied to them. Development uses `[envs.development].db` when it is set. Otherwise it binds every name used by any environment, taking the database from the first environment in name order, so most projects need no development bindings. To choose them yourself:

```toml
[envs.development]
db = { main = "main" }
```

Run one-off scripts with the app's bindings:

```bash
tako run bun scripts/seed.ts
```

`tako run` always runs locally and serves only development bindings. With `--env production` (or any other environment) the script gets no databases and Tako prints a warning: hosted databases are reachable only from deployed apps. Use `tako db shell`, `tako db export`, or a release command for production data.

The development endpoint listens on a random loopback port for the lifetime of the dev daemon or `tako run`. Its URL and token change between sessions; read them from the binding rather than copying them.

## Query and inspect

```bash
tako db status main --json
tako db shell main "SELECT count(*) FROM users" --json
tako db shell main
```

`status` reports the size, the app environments using the database on its server (`bindings`), those granted from other servers (`remote_grants`), and backup state: destination, when everything captured was last confirmed uploaded (`replicated_at_unix_secs`), the newest full snapshot, the last attempt, and the last error. Without a name it reports the databases this project uses in the selected network, including channel replay.

`shell` runs SQL with a full-access connection. With SQL as an argument it runs that statement and exits; with `--json` it prints `columns`, `rows`, `affected_row_count`, and `truncated`. Results stop at 1,000 rows and 8 MiB; use `export` for more. Each statement commits on its own: `BEGIN` is rejected rather than silently leaving later statements outside a transaction, so run multi-statement changes from a migration or a script. Without SQL it reads statements from standard input; an interactive terminal also accepts `.tables`, `.schema [table]`, and `.quit`. The shell has the same restrictions as apps.

## Back up and restore

Backups go to a private S3-compatible storage resource (no `public_base_url`): the `backup.storage` of the environment that binds the database, or `[db.<name>].backup` when set:

```toml
[envs.production]
db = { main = "main" }
backup = { storage = "private_backups" }

# Only to use another storage for one database:
# [db.main]
# backup = "other_backups"

[storages.private_backups]
provider = "s3"
bucket = "app-backups"
endpoint = "https://example.r2.cloudflarestorage.com"
region = "auto"
```

```bash
tako storage credentials private_backups --env production
tako deploy --env production
```

A deploy by a full client sends the destination and credentials to the database's server. Removing the backup storage and deploying stops backups. Moving to another storage starts a new history there, beginning with a full snapshot; the history in the earlier storage stays there (retention and `delete` reach only the current one), so remove `_tako/databases/<name>/` from it yourself once you no longer need it. A new database is not backed up until such a deploy. Backups provide point-in-time recovery even if all replicas are lost. Environments that bind the same database should use the same storage, since each full client's deploy sets it.

### Continuous backups

For replicated databases, the elected leader uploads committed Turso recovery images and changes to backup storage. A Raft majority commits each write before the client receives success. Uploads run separately. After losing the entire group, you can recover through the most recent uploaded transaction. The default retention window is seven days.

- **Full snapshots** restore on their own. The server captures one when backups start (after the server starts, a restore, import, or reset, or a new destination), once a day while the database changes, and on demand with `tako db backup <name>`.
- **Restore points** name a transaction: the state before a deploy's release command, before pending migrations, and before a restore, import, or reset replaces the database. Every full snapshot is a restore point too.
- **Retention** keeps the last 7 days of history in full. Older history is removed, except for the full snapshots it keeps longer: all of those from the last 24 hours, and the newest of each of the last 7 days and of each of the last 4 weeks. A restore point is removed with the history it names.

Uploads are encrypted with AES-256-GCM using the database's own key, which also authenticates each object's name, so an object cannot be swapped for another. The key is generated at `create` and kept in the encrypted network state, readable only by full clients, and on the database's server. Pages are compressed with LZ4. Objects are written under `_tako/databases/<name>/<generation>/` (`ltx/` for history, `points/` for restore points), where the generation is a random ID chosen at `create`, so a database created again under an earlier one's name never sees its backups. Segments over 1 GiB, such as the full snapshot of a large database, are uploaded in 64 MiB parts. A segment holds at most 64 GiB once compressed, the most one AES-GCM message encrypts, so a database whose compressed full snapshot is larger is not backed up: its status shows the error.

When storage fails, the server keeps capturing on its own disk and retries with backoff, at most 15 minutes apart, uploading everything once storage accepts it again; `tako db status` shows the last error. Stopping or upgrading the server uploads what is left first, for up to 20 seconds, and the rest when it starts again. A database that changes all the time makes about 8,600 uploads a day and one full snapshot a day.

A hosted export or restore materializes a portable SQLite file from the committed base and transaction log.

### Restore

```bash
tako db backups main
tako db restore main --at "2026-11-23 10:15"
tako db restore main --at 15m
tako db restore main --snapshot <id>
tako db restore main --latest
```

`backups` lists the window of time the database can be restored to and its restore points, newest first, with their IDs; `--json` prints `windows` (`from_unix_ms`, `to_unix_ms`, `from_transaction`, `to_transaction`) and `snapshots` (`id`, `created_at_unix_secs`, `reason`, `full`, `stored_bytes`). A restore takes exactly one of:

- `--at <time>`: the newest transaction captured at or before that time, given as a local time (`2026-11-23 10:15` or `2026-11-23 10:15:30`, read with the offset your time zone has on that date), an RFC 3339 time (`2026-11-23T10:15:00Z`), or an age (`90s`, `15m`, `2h`, `1d`). The confirmation shows the time with its offset; a time before every backup fails with the earliest restorable time.
- `--snapshot <id>`: a restore point from `backups`.
- `--latest`: the newest transaction uploaded, which recovers a lost or damaged copy.

A restore checks that the server has room, downloads only what it needs (the newest full snapshot at or before the target, then the transactions after it), verifies every checksum and the restored file's integrity before anything changes, then pauses the database and swaps it in. While a database is replaced, apps' requests to it get `503` responses. In-flight requests finish first; the replacement fails, leaving the database unchanged, if they take longer than 30 seconds. Before the swap, the server captures and uploads exactly the contents it replaces and records them as a restore point with reason `restore`, so restoring that point's `--snapshot` ID undoes the restore; the replaced file is also kept beside the database as `previous.sqlite` until the next replacement. The restored state then continues the history: `--latest` and later times include it.

Hosted channel replay uses this same backup destination and restore process. With no backup storage there is no backup. Restoring, importing or resetting a shared file affects all the apps that use it: their replay cursors reset and connected subscribers resync. It does not restore live presence or ephemeral messages. After moving its home, redeploy the affected environments with full access and have clients resync.

### Import and export

```bash
tako db export main ./main.sqlite
tako db import main ./main.sqlite
```

`export` downloads a consistent copy without pausing apps and refuses to overwrite an existing file. `import` replaces the database with a local SQLite file after verifying it on the server; when backups are configured, the current contents are backed up first and named with a restore point (reason `restore`). Only the main file is uploaded: stop writers and checkpoint the file (`PRAGMA wal_checkpoint(TRUNCATE)`) before importing a database that uses WAL. Imports are limited to 64 GiB. An import or export in progress is held by the server process, so a restart or upgrade of the server ends it; run the command again.

To move an app from a SQLite file in its data directory, create a hosted database, copy the file to your machine during a write freeze, import it, bind the database, and deploy the code that uses `tako.db`.

### Recover on another server

For a replicated database, restore through the elected leader. The replacement commits through Raft. A new deployment target joins the group during a full-access deploy. For a legacy single-home database, use the following recovery procedure.

```bash
tako db restore main --latest --server edge-b
tako deploy --env production
```

With `--server`, Tako creates the database on `edge-b` from its backups and records `edge-b` as its server in the network; `tako.toml` does not change. `--latest` restores everything the old server uploaded, so at most its last few seconds of writes are lost; `--at` and `--snapshot` work too. It reads the backups from the backup storage of an environment that binds the database. Deploy every app that binds it afterwards: until then, instances deployed earlier keep using the old copy, and a deploy gives new instances new tokens for `edge-b`.

When the old server is still running, its copy stays, and Tako stops its backups so it cannot prune the new copy's history. An old server that was unreachable during the move stops uploading on its own once it is back: the restore recorded `edge-b` as the database's holder in the backup storage. Until it notices, anything it still uploads stays apart from the new copy's history, which starts far above it, so a restore never mixes the two; once it notices, it stops capturing, also across restarts. The copy a move creates on `edge-b` uploads nothing until its restore has finished, so its empty file never becomes the latest state. Once every app is deployed, remove the old copy:

```bash
tako db delete main --server edge-a
```

That deletes only the copy on `edge-a`; the database, its network record, and its backups stay. If `edge-a` holds an earlier database of the same name instead (one deleted from the network while `edge-a` was unreachable), the command says so before deleting it, together with that database's backups. If the recovery itself fails, Tako removes the new copy on `edge-b` without touching the backups. If the move stops after the restore (for example, the network record could not be published), run the same command again: it finds its copy on `edge-b`, restores it again, and finishes the move. If that second restore fails, the copy on `edge-b` stays as it was, so the command can be run again. To abandon the move instead, remove that copy with `tako db delete main --server edge-b`, which gives the backups back to the copy the network still names; `tako db delete main` also removes such leftover copies from every reachable server of the network.

## Reset a database

```bash
tako db reset main
tako db reset main --local
```

`reset` replaces the database with an empty one that already has the project's migrations applied: they run on the new file before it replaces the old one, so apps never see the database without its schema, and a failing migration leaves it unchanged. On a server it pauses requests like a restore and, when backups are configured, first backs up the contents it replaces and names them with a restore point (reason `restore`), so `tako db restore main --snapshot <id>` undoes it. It asks for confirmation (`--yes` skips it) and refuses a database the `production` environment binds unless `--force` is passed. With `--local` it empties the development file, which `tako dev` may keep serving, and applies the development migrations.

## Delete a database

```bash
tako db delete main
```

For replicated resources, `delete` waits for the generation to have no active or retained release bindings. It then retires the generation and removes its replicas. Objects already uploaded to backup storage keep their original generation and recovery key. A later deployment that reuses the name creates a fresh generation. Use `tako delete --server <server>` to remove an application from a particular server and reconcile its storage there.

## Apps on other servers

An app on another server than its database's connects to its own server as usual. That server forwards the request over the network's private WireGuard transport to the database's server on port 9847, which the network firewall opens only to other servers. A full client's deploy grants the app environment the database on its server, and revokes grants the new release no longer uses only after its rollout succeeds, so the previous release keeps working until then; the grant comes with a key that the deploy hands to the app's servers, and forwarded requests must carry it, so other processes on a granted server cannot act for the environment. Tokens never leave the app's server. A deploy client keeps the bindings and keys a full client provisioned.

Targets share the same committed history. Tako elects a leader automatically. After an election, the ordinary binding follows the new leader. An in-flight operation can fail with an unknown commit outcome. Use idempotency keys for operations an application retries.

## Limits and security

- Each binding has its own random token. A token works only on the server that issued it and only for the databases its app environment binds. Binding tokens stay stable across deploys while a binding names the same database on the same server.
- During a rolling deploy, the old and new release's bindings are both active, so old instances keep working until they drain. A release command receives temporary bindings that are revoked when it finishes.
- SQL cannot reach other files or load code: `ATTACH` (including `VACUUM INTO '<path>'` and attachments named at run time), `load_extension`, and `fts3_tokenizer` are refused. Plain `VACUUM` works.
- Reading any `PRAGMA` is allowed. Connection settings such as `foreign_keys` and `defer_foreign_keys` can be changed, as can `user_version`, `application_id`, and `auto_vacuum`. Other writes, such as `journal_mode` or `synchronous`, are refused: Tako runs WAL with `synchronous = FULL`.
- `foreign_keys` is on for every connection. A statement may take at most 30 seconds to prepare and run, and the statements of one `sequence` (such as `executeMultiple`) share that limit; a statement waits up to 5 seconds for the write lock. A migration file's statements may run for 5 minutes together and wait up to 30 seconds for the write lock. Interactive transactions idle for 10 seconds are rolled back.
- Requests are limited to 32 MiB and 65,536 statements and batch steps, and a request's body must arrive within 30 seconds (otherwise `408`); a request that waits 30 seconds for one of the database's 32 request slots, or for room in the server's 256 MiB of buffered requests and cursor output, gets `503`, as does a pipeline whose results find no room left in that buffer (results stay counted until the response is sent); a connection that sends no request for 30 seconds, or stops reading its response for 30 seconds, is closed, and a server holds at most 1,024 connections per listener; responses are limited to 64 MiB, counted as encoded JSON, including column names and error messages; a single string, blob, or row is limited to 64 MiB, also on the cursor endpoint. Use a cursor (`@tursodatabase/serverless` `iterate`) or pagination for larger results.
- App SQL bindings are available to native releases. [Container and Compose releases](/docker/) cannot use them; their SDK-enabled services can use hosted replay through the channel runtime.
- A deploy client cannot change an environment's database bindings; a full client must deploy the change.
- Managing databases (`create`, `status`, `shell`, `backup`, `backups`, `restore`, `import`, `export`, `reset`, `delete`) requires full access. Every member that may deploy can read where databases live (`list` and deploys), record the restore point before their own release, and apply their own app's migrations; backup keys are readable only by full clients.
- Concurrent first deploys use the network catalog to reserve one generation for a name. An engine or service ownership conflict stops the deploy. Existing data groups commit independently of the catalog.

## Verify

1. Run `tako db status <name> --json` and confirm the server, `bindings` or `remote_grants`, and that `backup.replicated_at_unix_secs` is recent and `backup.last_error` is empty.
2. Run `tako db migration list` and confirm nothing is pending after a deploy.
3. Run `tako db shell <name> "SELECT count(*) FROM <table>" --json` to check known rows.
4. Run `tako db backups <name> --json` and confirm a window that ends within the last minute, and the restore point of the last deploy.
5. Before depending on backups, practice on a staging database: insert a row, wait 10 seconds, run `tako db restore <name> --at <a time before the insert>`, confirm the row is gone, then restore the `restore` point it recorded to get it back.
