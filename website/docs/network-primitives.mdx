---
title: Network Primitives
description: "Call private handlers, workflows, and channels by string address, with shared TypeScript inputs and results."
---

Use a string address to communicate with an app in the same private network:

| Operation | Behavior | Return value |
| --- | --- | --- |
| `call("users.lookup", input)` | Execute a network handler directly | Handler result |
| `workflow("mail.send-email").enqueue(payload)` | Queue durable work | Run ID |
| `workflow("mail.send-email").run(payload)` | Queue durable work and wait | Workflow result |
| `channel("web.progress").publish(message)` | Publish to the recipient's channel | Publication acknowledgment |

Network handlers execute without enqueueing. They use request/response transport and may still wait for network I/O, an idle app to start, or available execution capacity. Workflows run when a worker claims them. Channel publication does not wait for subscribers to process the message.

## Addresses and access

An address is `app.primitive`. Omit the namespace to select the current app: `workflow("send-email")`. The app portion is its `name` in `tako.toml`; there is no separate namespace setting. Primitive names contain 1–255 ASCII letters, digits, underscores, hyphens, or colons. Dots separate the app from the primitive.

Calls inherit the caller's deployment environment. `mail.send-email` from `web/staging` targets `mail/staging`. Addresses cannot select another environment, an arbitrary URL, or a public host. The server resolves current network placements and wakes an idle recipient when needed. Without native network membership, calls reach apps on the same server only.

Run both applications under the same `tako dev` daemon for local calls. App names must identify a single registered app; ambiguous development variants are rejected.

Any app in the same network and environment can invoke a declared recipient primitive. Type exports select what a consumer knows about; they are not an access-control list. Channel subscription authorization still applies to subscribers. Network publication uses the recipient's channel definition and lifecycle, rather than browser authorization callbacks. Channel params are validated against that definition; they do not create separate rooms or streams.

## Language support

| Capability                                    | JavaScript / TypeScript | Go HTTP SDK (`tako.sh`) | Rust SDK (`tako`) |
| --------------------------------------------- | ----------------------- | ----------------------- | ----------------- |
| Call a handler, workflow, or channel            | Yes                     | Yes                     | Yes               |
| Receive network calls for declared primitives | Yes                     | No                      | No                |
| Generate portable TypeScript contracts        | Yes                     | No                      | No                |

The recipient currently needs the JavaScript SDK's managed HTTP runtime and internal dispatcher. Go channel registration and the separate Go workflow worker SDK retain their existing local APIs; they do not install this dispatcher. Rust supports blocking calls and async calls with its `tokio` feature. Plain HTTP containers without the Tako runtime cannot use these SDK calls.

## Define the recipient

In the app named `mail`, define ordinary workflows and channels:

```ts
// mail/src/workflows/send-email.ts
import { defineWorkflow } from "tako.sh";

export default defineWorkflow<{ to: string; subject: string }>("send-email", {
  retries: 4,
  handler: async (payload, ctx) => {
    await ctx.run("deliver", () => sendEmail(payload));
  },
});
```

`sendEmail` is your application's delivery helper. Use a stable idempotency key with external providers when repeating an attempt could duplicate a side effect.

```ts
// mail/src/channels/delivery.ts
import { defineChannel } from "tako.sh";

export default defineChannel("delivery").$messageTypes<{
  sent: { messageId: string };
}>();
```

These definitions are available as `mail.send-email` and `mail.delivery`. The workflow name must match its filename. A channel uses the explicit name passed to `defineChannel`.

## Direct network handlers

Create one default-exported function per file under `<app_root>/network-handlers/`. Its filename supplies the address; no HTTP path or method is configured.

```ts
// users/src/network-handlers/lookup.ts
import { defineNetworkHandler } from "tako.sh";

export default defineNetworkHandler(async (input: { id: string }) => {
  return { id: input.id, displayName: "Ada" };
});
```

This handler is available as `users.lookup`. A plain default-exported function also works. Handlers may call other network handlers, publish channels, or start workflows. Return JSON data; no return value becomes `null`. Validate incoming data in your handler when it needs runtime validation: TypeScript contracts are compile-time checks.

<CodeGroup>

```ts JavaScript
import { call } from "tako.sh";
const user = await call("users.lookup", { id: "user-123" });
```

```go Go
import (
    "context"
    "encoding/json"
    "tako.sh"
)

func lookup(ctx context.Context, id string) (json.RawMessage, error) {
    return tako.Call(ctx, "users.lookup", map[string]string{"id": id})
}
```

```rust Rust
use serde_json::{Value, json};
use tako::network::Client;

async fn lookup(id: &str) -> std::io::Result<Value> {
    Client::from_env()?.call("users.lookup", json!({"id": id})).await
}
```

</CodeGroup>

Direct calls have no automatic retries. A timeout or disconnected caller does not prove the recipient stopped executing. Use an application idempotency key for effects that callers may retry. Calls that exceed network capacity fail promptly, including nested calls, so callers cannot occupy every slot while waiting for their descendants. Inside a workflow, wrap direct calls in `ctx.run` if their result should be checkpointed; the external effect still needs idempotency.

## Export and import types

`tako gen` keeps these files together beside the app's existing `tako.d.ts`, normally at the project root. If that file already lives in `src/` or `app/`, the other two files belong there too.

| File | Owner | Purpose |
| --- | --- | --- |
| `tako.d.ts` | Generated | Local declarations and typed address registries |
| `tako.imports.ts` | You | Named type exports selected from other apps |
| `tako.exports.d.ts` | Generated | Portable types for this app's own primitives |

For a monorepo, the existing declaration location determines where these files live; `app_root` determines where Tako discovers primitive implementations. No package export or output-path configuration is added automatically.

Run `tako gen` in the producer, then copy or publish `tako.exports.d.ts` through a package you own, or reference it from a sibling package. It contains standalone structural types with no imports back into producer implementations. Names use the primitive name in PascalCase plus `Workflow`, `Channel`, or `Handler`; conflicting names fail generation. Workflow contracts include payload and result, handler contracts include input and result, and channel contracts include params and messages. Values must be JSON data. Template-literal strings and readonly arrays/tuples are supported; unknown types remain `unknown`.

Select external types in one handwritten file:

```ts
// web/tako.imports.ts
export type { SendEmailWorkflow, DeliveryChannel } from "@acme/mail-types";
export type { LookupHandler } from "@acme/users-types";
```

Then run `tako gen` in the consumer. The generator reads each contract's kind and qualified address. The selected types apply to HTTP code, workflows, and network handlers throughout the app. Include `tako.d.ts` in the TypeScript project. Imported contracts are not re-exported in the consumer's generated `tako.exports.d.ts`.

For manually maintained shared types, use `NetworkWorkflow<Address, Payload, Result>`, `NetworkChannel<Address, Params, Messages>`, and `NetworkHandlerContract<Address, Input, Result>`. Type imports do not grant or restrict runtime access. Go and Rust use their own JSON structs; Tako does not generate cross-language types.

## Make calls

These examples enqueue the same recipient workflow:

<CodeGroup>

```ts JavaScript
import { workflow } from "tako.sh";

const runId = await workflow("mail.send-email").enqueue(
  { to: "reader@example.com", subject: "Welcome" },
  { id: "welcome:user-123" },
);
```

```go Go
import (
    "context"
    "tako.sh"
)

func sendWelcome(ctx context.Context) (string, error) {
    id := "welcome:user-123"
    result, err := tako.Enqueue(ctx, "mail.send-email",
        map[string]string{"to": "reader@example.com", "subject": "Welcome"},
        tako.NetworkEnqueueOptions{ID: &id})
    if err != nil { return "", err }
    return result.ID, nil
}
```

```rust Rust
use serde_json::json;
use tako::network::{Client, EnqueueOptions};

// Enable the tako crate's "tokio" feature for async calls.
async fn send_welcome() -> std::io::Result<String> {
    let client = Client::from_env()?;
    let result = client.enqueue("mail.send-email",
        json!({"to": "reader@example.com", "subject": "Welcome"}),
        EnqueueOptions { id: Some("welcome:user-123".into()), ..Default::default() },
    ).await?;
    Ok(result.id)
}
```

</CodeGroup>

Publish a channel message from server-side code:

<CodeGroup>

```ts JavaScript
import { channel } from "tako.sh";

await channel("mail.delivery").publish({
  type: "sent",
  data: { messageId: "msg-123" },
});
```

```go Go
func publishDelivery(ctx context.Context) error {
    _, err := tako.Publish(ctx, "mail.delivery", nil, "sent",
        map[string]string{"messageId": "msg-123"})
    return err
}
```

```rust Rust
async fn publish_delivery() -> std::io::Result<()> {
    Client::from_env()?.publish("mail.delivery", json!({}), "sent",
        json!({"messageId": "msg-123"})).await?;
    Ok(())
}
```

</CodeGroup>

The Go and Rust publication examples use the imports from their enqueue examples. Rust's `enqueue_blocking` and `publish_blocking` methods use the same arguments without `.await`.

## Workflow results

Return JSON data from a JavaScript workflow handler. Annotate the payload parameter to infer both input and output, or supply both generics to `defineWorkflow<Payload, Result>`. Supplying only the payload generic leaves the result type `unknown`.

```ts
// reports/src/workflows/generate.ts
import { defineWorkflow } from "tako.sh";

export default defineWorkflow("generate", {
  handler: async (input: { orderId: string }, ctx) => {
    return ctx.run("report", () => ({ url: `/reports/${input.orderId}.pdf` }));
  },
});
```

<CodeGroup>

```ts JavaScript
import { workflow } from "tako.sh";

const reports = workflow("reports.generate");
const id = await reports.enqueue({ orderId: "o1" });
const report = await reports.result(id, { timeout: "30s" });
// Or enqueue and wait in one operation:
const another = await reports.run({ orderId: "o2" }, { timeout: "30s" });
```

```go Go
// Imports: context, encoding/json, time, and tako.sh.
func reportResult(ctx context.Context, id string) (json.RawMessage, error) {
    ctx, cancel := context.WithTimeout(ctx, 30*time.Second)
    defer cancel()
    return tako.Result(ctx, "reports.generate", id)
}
```

```rust Rust
// Imports: tako::network::Client and serde_json::Value.
async fn report_result(id: &str) -> std::io::Result<Option<Value>> {
    let state = Client::from_env()?.result("reports.generate", id).await?;
    match state {
        Some(run) if run.status == "succeeded" => Ok(Some(run.result)),
        Some(run) if run.status == "pending" || run.status == "running" => Ok(None),
        Some(run) => Err(std::io::Error::other(run.error.unwrap_or(run.status))),
        None => Err(std::io::Error::other("run missing or no longer retained")),
    }
}
```

</CodeGroup>

JavaScript `.result()` and Go `Result` poll until the run finishes or the caller's timeout/cancellation occurs. Rust `result` reads the current state once; poll pending/running states with your chosen deadline. Rust also provides `call_blocking` and `result_blocking`. JavaScript defaults to waiting without a timeout. Its `WorkflowResultError` exposes `runId` and `status` (`dead`, `cancelled`, `missing`, or `timeout`). A wait timeout does not cancel the workflow; use the retained run ID to retrieve its result later. Results are retained with workflow history, for at least 184 days by default. See [Workflows](/workflows/#storage-and-multiple-servers).

Inside another JavaScript workflow, `.run()` acts as a durable child call. Tako checkpoints a stable child ID before enqueueing, reuses that ID if the acknowledgment is lost, and checkpoints the terminal outcome. A pending child defers the parent and releases its worker slot without consuming a retry. Replay resumes waiting for the same child; a cached result needs no further network call. Local imported workflow handles provide the same `.run()` and `.result()` methods.

```ts
const report = await workflow("reports.generate").run(
  { orderId: input.orderId },
  { step: "generate-report" },
);
```

The optional `step` identifies the call within its enclosing durable step; otherwise calls use their order. Keep names, order, target, and payload stable on replay. Calls inside named `ctx.run` steps have separate scopes, so skipping a cached step does not shift later calls. `.enqueue()` alone is detached: supply a stable `id` if it can repeat. Retention still bounds child ID deduplication; retain child history long enough for parent retries. Go's workflow worker API does not provide this automatic child-call behavior or typed handler return values.

## Retries and verification

The recipient workflow owns its execution policy. The default is two retries after the first attempt. Its `retries` setting applies unless the caller overrides it with JavaScript `retries` or Go/Rust `MaxAttempts`/`max_attempts`, which count total attempts. Retry timing comes from the recipient's workflow backoff settings. See [Workflows](/workflows/).

Network delivery is attempted once. Use a stable enqueue `id` when retrying an uncertain response: the recipient reuses a retained run when its workflow and payload match. Channel publication has no run ID or subscriber acknowledgement; repeating publication can deliver another message. A calling workflow can place the send in a checkpointed step and use its own retry policy.

To verify, generate types in both applications, typecheck the consumer, and start both with `tako dev`. Enqueue from a server-side handler and inspect the recipient's workflow logs. For a channel, subscribe to the recipient and publish from the caller. In deployment, use apps in the same environment and network; `/_tako/network` is rejected on public ingress.
